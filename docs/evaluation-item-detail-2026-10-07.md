## 1-① VPC, Public Subnet, Internet Gateway, Route Table(`0.0.0.0/0`→IGW)이 구성되어 있는가?

**① 뜻**: 리소스 4종이 "존재"하는지가 아니라 **서로 연결되어 하나의 통로를 이루는지**를 본다.
VPC → IGW 연결(attachment), 서브넷 → 라우트 테이블 연결(association), 라우트 테이블 → IGW로 가는 기본 경로, 이 3개의 연결이 전부 필요하다.

**② 평가위원 의도**: 초보자가 가장 많이 틀리는 지점이 "라우트만 만들고 IGW를 VPC에 붙이지 않음", "서브넷을 다른 라우트 테이블에 붙임"이다. 그래서 화면에서 **연결 관계**를 확인한다.

**③ 우리 실제 상태** (`infra/cloudformation.yml`):
| 요소 | 값 |
|---|---|
| VPC | `10.0.0.0/16`, DNS 지원·호스트네임 활성, 태그 `Project=b6-1`, `Name=b6-1-vpc` |
| Public Subnet | `10.0.1.0/24`, 가용영역 1번째, **MapPublicIpOnLaunch=true**, `Name=b6-1-public-subnet` |
| Internet Gateway | `b6-1-igw` + VPC에 attach (별도 리소스 `InternetGatewayAttachment`) |
| Route Table | `b6-1-public-rt` + 기본 경로 `0.0.0.0/0 → IGW` + 서브넷 association |

**④ 보여줄 화면**: `evidence/2026-10-03/10-ebs-vpc-route.*`, `27-iam-network-health.*`, `18-network-ebs-reaudit.*`, `docs/architecture.svg`
재배포했다면: VPC 콘솔 → 라우트 테이블 → "Routes" 탭(0.0.0.0/0 → igw-xxx)과 "Subnet associations" 탭을 함께 보여준다.

**⑤ 답변 대본**:
> "서울 리전에 VPC `10.0.0.0/16`을 만들고, 그 안에 퍼블릭 서브넷 `10.0.1.0/24`를 뒀습니다. Internet Gateway를 VPC에 연결하고, 서브넷의 라우트 테이블에 기본 경로 `0.0.0.0/0`을 IGW로 보내도록 넣었습니다. 라우트 테이블은 서브넷에 association까지 되어 있어서, EC2가 외부 목적지로 나가고 응답을 받을 수 있습니다. 이 구성은 CloudFormation 템플릿의 리소스 6개(VPC·IGW·Attachment·Subnet·RouteTable·Route·Association)로 코드에 그대로 남아 있습니다."

**⑥ 배경 개념**: 사설 대역(`10.0.0.0/16`)은 인터넷 라우터가 목적지로 인식하지 못한다. 그래서 VPC 경계에서 공인 주소로 바꿔주는 IGW가 필요하고, "외부로 나가는 길"을 라우트 테이블 기본 경로로 지정해야 한다. IGW는 NAT 장치가 아니라 **1:1 매핑**이므로 인스턴스에도 퍼블릭 IPv4가 있어야 한다(우리 서브넷은 MapPublicIpOnLaunch=true, 인스턴스도 AssociatePublicIpAddress=true).

**⑦ 함정**: "프라이빗 서브넷은 없나?" → "과제 최소 구성이 퍼블릭 1개이고, EC2가 인터넷에서 직접 접속되어야 하는 구조라서 퍼블릭만 뒀습니다. 계층 분리가 필요하면 프라이빗 서브넷 + NAT가 추가로 필요합니다."

## 1-② EC2에 SSH로 접속 가능하며, 웹 서버가 실행 중인가?

**① 뜻**: 두 가지를 동시에 본다. (a) 22번으로 실제 접속되는가, (b) 서버에서 웹 서비스가 살아 있는가.

**② 평가위원 의도**: 인스턴스가 `running`인 것과 서비스가 정상인 것은 다르다. `docker ps`가 healthy이고 내부에서 `/health`가 200인지까지 보려 한다.

**③ 우리 실제 상태**:
- Amazon Linux 2023, `t3.micro` 1대, IMDSv2 강제(HttpTokens required), 퍼블릭 IPv4 자동 할당
- UserData: docker 설치 → `git fetch`로 고정 커밋 `6bc1076c4311cc2685b483ca326be8bc7e5f4bb1` 체크아웃 → `docker build` → `docker run --restart unless-stopped -p 80:80`
- 배포 성공을 CloudFormation `CreationPolicy`(ResourceSignal 15분)로 검증. 즉 "스택이 완료됐다 = 컨테이너 /health가 OK를 반환했다"가 배포 시점에 이미 보장됨
- 실제 확인 기록: `docker ps` healthy, 컨테이너 내부 `curl localhost/health` 200, 배포 커밋 파일 확인

**④ 보여줄 화면**: `13-ssh-docker-healthy.*`, `29-current-ssh-docker.*` (SSH 세션 원본 TXT)
※ `13`의 JPG는 PC에서 SSH로 받은 원본 출력을 CloudShell 화면에 표시한 캡처다. "CloudShell에서 SSH를 실행했다"고 말하지 않는다.

**⑤ 답변 대본**:
> "SSH로 접속하면 Amazon Linux 2023 커널 버전이 보이고, `docker ps`에 `b6-1-web` 컨테이너가 healthy 상태로 뜹니다. 컨테이너 안에서 `curl localhost/health`를 실행하면 200과 `OK`가 나옵니다. 그리고 서버가 배포한 코드가 무엇인지 확인하려고 커밋 해시를 파일로 남겼습니다 — `6bc1076...`입니다. 배포 자체는 CloudFormation이 cfn-signal로 성공을 확인한 뒤에야 스택이 완료되도록 만들어서, 스택이 완료 상태라는 것이 곧 헬스체크 통과를 뜻합니다."

**⑥ 배경 개념**: `docker run -p 80:80`은 호스트 80번을 컨테이너 80번에 포워딩(게시)한다. 그래서 SG가 80을 허용하면 컨테이너의 Nginx까지 도달한다. `--restart unless-stopped`는 인스턴스 재부팅 후에도 서비스가 자동 복구되게 한다.

**⑦ 함정**: 재배포하면 새 키페어/개인 키가 필요할 수 있다. 키가 없으면 SSH 재현이 불가하므로 배포 전에 확인한다. (개인 키는 저장소에 저장하지 않는다.)

## 1-③ 보안 그룹 인바운드가 "필요 포트만" 허용하며, SSH(22)가 특정 IP로 제한되어 있는가?

**① 뜻**: 인바운드 규칙 목록을 전부 펼쳐 보고, (a) 서비스에 필요한 포트만, (b) SSH 소스가 개인 IP로 좁혀졌는지, (c) 전체 포트 공개가 없는지 확인한다.

**② 평가위원 의도**: 이 항목은 **보안 위생**을 본다. 22번을 `0.0.0.0/0`으로 열어둔 흔한 실수를 잡아낸다.

**③ 우리 실제 상태** (`WebSecurityGroup`): 인바운드 **두 규칙뿐**
| 방향 | 프로토콜 | 포트 | 소스 | 설명 |
|---|---|---|---|---|
| Inbound | TCP | 80 | `0.0.0.0/0` | Public HTTP |
| Inbound | TCP | 22 | `AllowedSshCidr` (개인 IPv4 `/32`) | SSH from learner public IP only |
| Outbound | 전체 | - | `0.0.0.0/0` | 패키지·이미지 다운로드 |

추가 안전장치: 템플릿 `Rules.RejectPublicSsh`가 `AllowedSshCidr = 0.0.0.0/0`이면 **스택 생성 자체를 거부**하고, 파라미터 `AllowedPattern`도 `/32` 형식만 허용하며, `deploy-stack.sh`는 전체 공개와 root 배포를 스크립트 단에서 막는다.

**④ 보여줄 화면**: `09-iam-ec2-security-group.*`(인바운드 전체 목록), `18-network-ebs-reaudit.*`
재배포했다면: EC2 → 인스턴스 → 보안 탭 → SG → 인바운드 규칙 "전체 보기".

**⑤ 답변 대본**:
> "인바운드 규칙은 두 개입니다. HTTP 80은 인터넷 전체에서, SSH 22는 제 개인 IP 하나(`/32`)에서만 허용합니다. 전체 포트(0-65535) 허용 규칙도, IPv6 인바운드도 없습니다. 아웃바운드는 패키지와 Docker 이미지를 받아야 해서 전체를 허용했는데, 이건 인바운드 노출과 다른 방향입니다. 게다가 템플릿 규칙(`RejectPublicSsh`)과 배포 스크립트가 SSH `0.0.0.0/0`을 아예 거부하도록 만들어서, 실수로도 전체 공개가 안 되게 했습니다."

**⑥ 배경 개념**: SG는 **stateful**이라 인바운드를 허용하면 응답은 자동으로 나간다. 그래서 아웃바운드 전체 허용이 보안 사고는 아니다. 최소 권한 원칙은 "필요한 것만, 가능한 좁게, 임시로 연 것은 즉시 제거"이다.

**⑦ 함정**: "집 IP가 바뀌면?" → SSH가 막힌다. 이때 SG를 전체로 여는 대신 규칙의 소스를 갱신하거나, SSM Session Manager 같은 무(無)포트 접속으로 전환하는 것이 정답이다.

## 2-① "외부 → IGW → Subnet → EC2" 흐름을 다이어그램 기준으로 설명할 수 있는가?

**① 뜻**: 그림을 가리키며 논리적 순서로 말로 풀어내는 것.

**② 평가위원 의도**: 구조를 외웠는지보다 **"어디서 막히면 무슨 증상이 나는지"**를 이해했는지 본다.

**⑤ 답변 대본(약 60초)**:
> "사용자가 브라우저에서 공인 IP로 접속합니다. 요청은 인터넷을 지나 VPC의 Internet Gateway로 들어옵니다. IGW는 VPC 경계이고, 그다음 라우트 테이블이 이 서브넷의 트래픽이라는 걸 알고 기본 경로로 연결합니다. 퍼블릭 서브넷 안에는 EC2가 있고, 도착하기 전에 Security Group이 80번 포트를 허용하는지 검사합니다. 통과하면 EC2의 퍼블릭 IPv4로 들어가고, 호스트의 80번은 Docker가 게시한 컨테이너 80번으로 전달됩니다. 컨테이너 안의 Nginx가 요청을 받아 `index.html` 또는 `/health`를 응답합니다. 그래서 이 중 한 단계라도 빠지면 접속이 실패하고, 순서대로 위에서부터 확인합니다."

**⑥ 배경 개념**: 이 경로에서 "외부에 공개되는 지점"은 IGW와 SG, 두 곳이다. IGW는 VPC 차원의 연결, SG는 인스턴스 차원의 필터다.

**⑦ 함정**: 다이어그램에 Docker/Nginx 계층이 있으면 그 부분까지 짚어야 한다. "EC2 = 웹서버"로 뭉뚱그리면 2-③에서 약해진다.

## 2-② 보안 그룹 규칙을 어떤 기준으로 최소화했는지(허용/미허용 포트) 설명할 수 있는가?

**⑤ 답변 대본**:
> "기준은 세 가지입니다. 첫째, 서비스가 실제로 쓰는 포트만 연다 — HTTP 80. 둘째, 관리 목적 포트는 소스를 최대한 좁힌다 — SSH 22는 내 IP `/32`. 셋째, 나머지는 열지 않는다 — DB 포트, 원격 데스크톱, 전체 포트 허용, IPv6 인바운드는 모두 없습니다. 아웃바운드는 패키지·이미지 다운로드를 위해 열어뒀는데, 인바운드와 달리 외부에서 들어오는 통로가 아닙니다. 그리고 템플릿 자체에 SSH 전체 공개를 거부하는 규칙을 넣어서 실수 방지도 했습니다."

**⑥ 배경 개념**: 최소화의 축은 **포트 수**, **소스 범위**, **유지 시간**이다. 소스 범위를 `/32`로 좁히는 것이 포트를 닫는 것만큼 중요하다.

## 2-③ A 또는 B를 선택했고, 그 선택을 위해 무엇을 어떻게 구성했는지 설명할 수 있는가?

**⑤ 답변 대본**:
> "A를 선택했습니다. 이유는 사람이 보는 화면까지 확인하는 것이 '인터넷에 공개됐다'는 증명에 더 직접적이라고 판단했기 때문입니다. A를 위해 구성한 것은 ① SG 인바운드 80 전체 허용, ② 서브넷의 퍼블릭 IPv4 자동 할당, ③ 컨테이너 80번 게시(`-p 80:80`), ④ Nginx 루트에 `index.html` 배치입니다. B도 함께 준비했습니다 — Nginx에 `location = /health`를 두어 200과 `OK`를 반환하게 했고, Dockerfile의 HEALTHCHECK가 같은 경로를 검사합니다. 그래서 컨테이너 상태 확인, 배포 성공 판정(cfn-signal), 외부 자동 검증을 모두 `/health`로 일관되게 할 수 있었습니다."

**⑥ 배경 개념**: A와 B는 경로가 다르지 않다. 같은 80번 포트, 같은 Nginx다. 다른 것은 **응답 내용**(HTML vs `OK`)과 **검증 자동화 용이성**이다.

**⑦ 함정**: "B만 했어도 되는데 왜 둘 다?" → "둘 다 만드는 비용이 거의 없고, A는 사람용, B는 자동화용으로 쓰임이 달라서요."

**⑤ 답변 대본**:

# 항목 3 — 이해 심화 (PASS/FAIL)

## 3-① Public Subnet Route Table의 기본 경로(`0.0.0.0/0`→IGW)가 필요한 이유를 설명할 수 있는가?

**⑤ 답변 대본**:
> "서브넷 안의 EC2는 사설 IP `10.0.1.x`를 씁니다. 외부 임의의 목적지로 나가는 트래픽은 라우트 테이블에서 '어디로 보낼지' 결정되는데, 목적지 대역별 경로가 다 있지 않습니다. 그래서 기본 경로 `0.0.0.0/0`이 필요하고, 그 대상을 IGW로 지정해야 VPC 밖으로 나갈 수 있습니다. 이 경로가 없으면 인바운드 요청이 도착해도 응답을 되돌려 보낼 수 없어서, 결과적으로 접속이 안 됩니다. IGW는 VPC에 attach되어 있어야 하고, 인스턴스에는 퍼블릭 IPv4가 있어야 합니다 — 세 조건이 함께 성립해야 '퍼블릭'이 됩니다."

**⑦ 심화 질문 대비**: "라우트만 있으면 되나?" → 아니다. IGW attach + 퍼블릭 IPv4 + SG 허용까지 있어야 한다.

## 3-② Security Group과 IAM의 책임 범위 차이를 설명하고, "최소 권한"이 왜 필요한지 설명할 수 있는가?

**⑤ 답변 대본**:
> "Security Group은 **네트워크 계층**에서 인스턴스 앞으로 오는 패킷을 거릅니다. IAM은 **컨트롤 플레인**에서 사람이나 프로그램이 AWS API를 호출할 권한을 정합니다. 그래서 SG에서 80번을 열어도 AWS를 조작할 권한이 생기지 않고, IAM 권한이 넓어도 네트워크가 막히면 서버에 못 들어갑니다. 최소 권한이 필요한 이유는 사고 반경을 줄이기 위해서입니다. 실제 구현은 두 정책으로 나눴습니다 — CloudFormation 스택 관리용과 EC2 작업용. 조건으로 서울 리전, 정확한 스택 이름, 태그, 인스턴스 타입 `t3.micro`, IMDSv2, 암호화 gp3 8GiB 이하, 키페어 `b6-1-key`만 허용합니다. 즉 실수로도 큰 인스턴스나 다른 VPC에 리소스를 만들 수 없습니다. 권한이 부족하면 관리자 권한을 붙이지 않고, 거부된 작업·대상·조건을 확인해 필요한 문장만 추가합니다."

**⑥ 배경 개념**: SG과 IAM은 "막는 대상"이 다르다. SG = 패킷, IAM = API 호출. 이 구분은 항목4-②의 답변과 직결된다.

## 3-③ SSH(22) 또는 DB 포트를 `0.0.0.0/0`으로 열면 안 되는 이유와 대안을 설명할 수 있는가?

**⑤ 답변 대본**:
> "인터넷 전체에 열면 스캔과 브루트포스 시도가 바로 들어옵니다. SSH는 초당 수천 건의 로그인 시도가 들어오는 게 일상이고, 포트를 바꾸는 건 보안이 아니라 단순 회피일 뿐입니다. DB 포트를 열면 자격 증명 탈취·데이터 유출 위험이 큽니다. 그리고 관리 포트를 임시로 열었다가 잊는 사고가 실제로 흔해서, 과제 제약에도 'SSH는 내 IP만'이 명시되어 있습니다. 대안은 ① 내 IP `/32`로 좁히기, ② SSM Session Manager 같은 무포트 접속, ③ Bastion을 두더라도 관리 대역만 허용, ④ SG-to-SG 참조로 앱 계층만 DB에 접근, ⑤ VPC 내부 통신 유지, ⑥ 필요 시 VPC 피어링·VPN입니다. 임시로 연 규칙은 즉시 제거하는 것을 운영 규칙으로 두었습니다."

**⑤ 답변 대본**:
