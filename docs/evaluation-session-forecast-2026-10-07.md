### 항목2 — 설명

- **네트워크 흐름(다이어그램)**: "사용자 브라우저 → 인터넷 → Internet Gateway → Public Subnet의 Route Table(`0.0.0.0/0`→IGW) → Security Group의 80 허용 검사 → EC2의 퍼블릭 IPv4 → Docker 컨테이너(80:80) → Nginx → `index.html` 또는 `/health`."
- **SG 최소화 기준**: "허용한 것은 서비스에 실제로 필요한 80(전체 공개)과 관리용 22(내 IP `/32`) 두 개이고, 그 외 포트·전체 포트·IPv6 인바운드는 열지 않았습니다. 필요 포트를 먼저 정하고, 소스는 가능한 좁게(`/32`), 임시로 연 규칙은 즉시 제거했습니다."
- **A/B 선택 근거**: "A와 B를 모두 확보한 뒤 A를 대표 증거로 선택했습니다. 사람이 보는 화면 로딩까지 증명하려고 A를, 자동 검증·장애 확인에 쓰려고 B를 남겼습니다. 그래서 항목4의 장애 점검 순서에도 `/health`를 사용합니다."
- **추적·정리 기준**: "① 모든 리소스에 `Project=b6-1` 태그, ② 이름 규칙(스택 `b6-1-learning`, 키 `b6-1-key`, LT 등), ③ `docs/cleanup-checklist.md`에 실제 리소스 ID를 기록해 삭제 여부를 대조. 스택 밖 리소스(키페어)는 별도로 추적했습니다."

### 항목3 — 이해 심화

- **Public Subnet 기본 경로가 필요한 이유**: "VPC 안은 사설 대역이라, 외부 목적지로 나가는 경로가 없으면 요청은 들어와도 응답이 돌아가지 못합니다. 그래서 서브넷 Route Table에 `0.0.0.0/0`→IGW를 두고, IGW를 VPC에 붙이고, 인스턴스에 퍼블릭 IPv4를 줘서 'Public'이 됩니다."
- **SG와 IAM의 차이/최소 권한**: "SG은 인스턴스 앞에서 **네트워크 패킷**을 거르고, IAM은 사람/프로그램이 **AWS API를 호출할 권한**을 정합니다. 층이 다르므로 SG로 80을 열어도 AWS 조작 권한은 생기지 않습니다. 최소 권한은 필요한 API + 필요한 리소스 ARN + 조건만 허용하는 것으로 구현했습니다."
- **SSH/DB 포트를 `0.0.0.0/0`으로 열면 안 되는 이유와 대안**: "인터넷 전체에 열면 브루트포스·스캔에 바로 노출되고, 임시로 열어둔 포트를 잊으면 침해와 과금 사고로 이어집니다. 대안은 내 IP `/32`, SSM Session Manager, Bastion + 내 IP, SG-to-SG 참조, VPC 내부 통신 유지입니다."
- **트러블슈팅 가설→검증 순서/로그 활용**: "증상 → 원인 가설 → 검증(권한 dry-run·readback, CLI 출력) → 조치(정책 범위를 대상 리소스로 축소) → 결과(재시도 성공) → 재발 방지 순서로 기록했습니다. 실제로 시작 템플릿 권한과 네트워크 태그 갱신 실패 2건을 이 순서로 해결했습니다." → 근거: `docs/troubleshooting.md`, `04~08`, `14`, `31~33`

### 항목4 — 응용·장애 대응

- **외부 접속 실패 시 점검 순서**: "① 라우팅(RT 기본 경로, IGW attach) → ② SG 인바운드(80, 소스) → ③ 퍼블릭 IP 존재 여부(도메인이 있으면 DNS) → ④ 서버 프로세스(`docker ps`/healthy, 포트 리슨) → ⑤ 로그(`docker logs`, Nginx access/error). `LEARNING.md`에 '어느 한 단계라도 빠지면 실패, 그래서 위에서부터 확인'으로 정리해 두었습니다."
- **IAM 권한 부족 시 최소 범위 찾기**: "거부 이벤트에서 어떤 API와 어떤 리소스 ARN이 거부됐는지 확인하고, 그 대상 + 조건으로만 허용을 추가한 뒤 dry-run/readback으로 재검증합니다. 관리자 권한을 붙이는 방식은 쓰지 않습니다. 이번에도 정리 단계에서 키페어·스택 삭제 권한을 정확한 리소스로 추가해 해결했습니다." → 근거: `40-key-delete-denied`, `43-iam-cleanup-retry-key-deleted`, `docs/deployment-permissions.md`
- **인스턴스 2대로 확장**: "현재 구조의 병목은 **인스턴스 1대**와 그 안의 컨테이너 1개(단일 장애점)입니다. 서브넷이 1개라 다중 AZ도 안 됩니다. 2대로 늘리려면 ① 서로 다른 AZ에 서브넷 2개 이상, ② ALB + Target Group(헬스체크 `/health`), ③ Auto Scaling 그룹, ④ 공인 트래픽은 ALB만 받고 EC2는 ALB SG에서만 80 허용으로 변경이 필요합니다. 정적 사이트라 세션 상태가 없어 수평 확장이 단순하고, 대가는 ALB 비용과 구조 복잡도입니다."
- **예상치 못한 Billing 항목 발견 시**: "Billing/Cost Explorer에서 서비스·리전별로 큰 항목을 좁히고, `Project=b6-1` 태그로 소유 리소스를 추적합니다. 의심 대상은 미연결 EIP, NAT Gateway, RDS, 남은 스냅샷·EBS, 퍼블릭 IPv4 주소 요금입니다. 삭제·Release 후 다음 날 다시 확인합니다(청구 반영 지연). 이번 실습에서도 삭제 후 IAM으로 Bills·Billing 홈을 조회해 0.00을 확인했습니다." → 근거: `46`, `47`, `44`

## 4. 꼬리질문 대비 카드 (짧은 답)

| 예상 꼬리질문 | 한 줄 답 |
|---|---|
| 왜 t3.micro 한 대인가? | 프리 티어 대상 micro 1대 제약을 그대로 지켰고, EBS는 암호화 gp3 8GiB만 사용했다. |
| 왜 CloudFormation인가? | 반복 입력을 줄이고 같은 구성을 재현하기 위해서다. 콘솔에서 VPC→서브넷→RT→SG→EC2 연결을 직접 확인해 이해를 대체하지 않았다. |
| 왜 Docker인가? | 로컬과 EC2에서 같은 실행 환경을 쓰고 `/health`로 검증을 단순화하려고. 대가는 이미지/레이어 학습 비용. |
| 왜 RDS/ALB/Route 53은 없나? | QUEST.md에서 이들은 소개·예시이고, 최소 실행 구성은 VPC+EC2로 지정되어 있다. 비용을 줄이려 미생성했고 실제 조회에서도 0개다. |
| 왜 다 지웠나? | 과제 제약이 "실습 종료 후 모든 리소스 종료/삭제"이기 때문. 삭제 전 증거를 남기고, 삭제 과정도 전부 기록했다. |
| 키페어는 IAM으로 만들었나? | 실제 생성은 준비 단계였고 IAM에서는 dry-run으로 권한만 확인했다. 실제 IAM 삭제는 성공했다. 이 구분을 그대로 말한다. |
| 루트를 썼나? | 스택 생성·업데이트·조회·정리는 IAM `b6-1-learner`로 했다. 계정·정책 준비 단계의 루트 사용은 별도 문서에 기록했다. |
| HTTPS는? | 도메인이 없어 미구현. `docs/https-plan.md`에 후속 계획을 남겼고, 가짜 인증서로 완료 처리하지 않았다. |
| 청구 0원 확정인가? | 아니다. 10월 예상 USD 0.00이고 최종 청구 확정은 아니다. 반영 지연을 감안해 재확인 계획을 세웠다. |
| 이 화면 오늘 건가? | 캡처 시각과 실행 시각을 말한다. 과거 실행 증거를 현재 화면처럼 말하지 않는다. |
