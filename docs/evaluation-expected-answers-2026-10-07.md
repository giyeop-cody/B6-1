# 제1장 항목 1 — 실물 확인

## 항목 1-①

> **문항**: VPC, Public Subnet, Internet Gateway, Route Table(`0.0.0.0/0` → IGW)이 구성되어 있는가?

### 예상 답안 (구두)

> “서울 리전에 VPC `10.0.0.0/16`을 만들고 그 안에 퍼블릭 서브넷 `10.0.1.0/24`를 배치했습니다. Internet Gateway를 생성해 **VPC에 연결(attach)**했고, 그 다음 퍼블릭 서브넷이 사용하는 라우트 테이블 `b6-1-public-rt`에 **기본 경로 `0.0.0.0/0` → IGW**를 추가했습니다. 마지막으로 그 라우트 테이블을 **서브넷에 연결(association)**했습니다. 이 구성은 CloudFormation 템플릿에 리소스로 그대로 남아 있어서 같은 환경을 다시 만들 수 있습니다. 콘솔 라우팅 테이블의 ‘경로’ 탭에서 `0.0.0.0/0 → igw-…`가, ‘서브넷 연결’ 탭에서 서브넷이 확인됩니다.”

### 답안 해설 — 세 동작은 서로 다르다

| # | 동작 | 비유 | 리소스 | 없으면 |
|---|---|---|---|---|
| ① | IGW를 VPC에 **attach** | 대문을 울타리에 연결 | `InternetGatewayAttachment` | 인터넷 진입 자체가 불가 |
| ② | 라우트 테이블에 **경로 추가** | 안내판에 “나머지 전부 → 대문” 한 줄 | `DefaultPublicRoute` | 나가는 길·응답 경로가 없어 timeout |
| ③ | 라우트 테이블을 서브넷에 **association** | 어느 마당이 어느 안내판을 쓰는지 | `PublicSubnetRouteTableAssociation` | 만든 경로가 적용되지 않음 |

- `0.0.0.0/0`의 의미: 앞 0비트만 고정 = **모든 IPv4 주소** = “표에 따로 적히지 않은 모든 목적지”(기본 경로).
- 템플릿에 `DependsOn: InternetGatewayAttachment`를 넣어 **attach 완료 후 경로 생성** 순서를 코드로 강제했다.
- **“퍼블릭”은 플래그가 아니라 결과**다: ① `0.0.0.0/0 → IGW` ② IGW attach ③ 인스턴스 퍼블릭 IPv4 — 세 조건이 모두 성립해야 한다.

### 근거

| 구분 | 자료 |
|---|---|
| 화면 | VPC 콘솔 → 라우팅 테이블 → `b6-1-public-rt` → 경로 탭 + 서브넷 연결 탭 / 인터넷 게이트웨이 상태 `Attached` |
| 증거 | `evidence/2026-10-03/10-ebs-vpc-route.txt`, `18-network-ebs-reaudit.txt`, `27-iam-network-health.txt` |
| 코드 | `infra/cloudformation.yml` — `Vpc`, `InternetGateway`, `InternetGatewayAttachment`, `PublicSubnet`, `PublicRouteTable`, `DefaultPublicRoute`, `PublicSubnetRouteTableAssociation` |
| 그림 | `docs/architecture.svg`, `docs/architecture.pdf` |

### 연계 질문

| 예상 질문 | 답변 |
|---|---|
| IGW는 무슨 장치인가? | “VPC 경계의 출입구입니다. NAT처럼 주소를 변환하지 않고 **1:1**이므로 인스턴스에 퍼블릭 IPv4가 따로 필요합니다.” |
| IGW 만들면 자동으로 붙나? | “아닙니다. 만드는 것과 VPC에 연결하는 것은 **별개 리소스**입니다.” |
| attach만 하고 경로를 안 넣으면? | “나가는 길을 몰라 인터넷이 안 됩니다. 인바운드가 도착해도 응답을 내보낼 수 없어 접속 실패로 보입니다.” |
| VPC 내부 통신도 되나? | “됩니다. `10.0.0.0/16 → local` 경로가 자동으로 있어서 attach·기본 경로와 무관하게 성립합니다.” |
| `0.0.0.0/0`은 IPv6도 포함하나? | “아닙니다. IPv6는 `::/0`으로 따로 씁니다. 이 VPC는 IPv6를 사용하지 않습니다.” |
| 프라이빗 서브넷은? | “과제 최소 구성이 퍼블릭 1개이고 EC2가 인터넷에 직접 공개되어야 하는 구조라서 퍼블릭만 두었습니다.” |
| 가용영역은? | “`GetAZs`의 첫 번째 AZ 한 곳입니다. 다중 AZ는 확장 시나리오(항목4-③)에서 설명합니다.” |

## 항목 1-②

> **문항**: EC2에 SSH로 접속 가능하며, 웹 서버가 실행 중인가?

### 예상 답안 (구두)

> “Amazon Linux 2023, `t3.micro` 인스턴스 1대입니다. SSH로 접속하면 커널과 OS가 확인되고, `docker ps`를 실행하면 `b6-1-web` 컨테이너가 **healthy** 상태로 표시됩니다. 컨테이너 안에서 `curl localhost/health`를 실행하면 `200 OK`가 반환됩니다. healthy는 Dockerfile의 `HEALTHCHECK`가 30초마다 `/health`를 검사한 결과입니다. 또한 배포는 컨테이너가 정상이 되면 `cfn-signal`로 CloudFormation에 완료 신호를 보내도록 만들어서, **스택이 완료 상태라는 것 자체가 서비스 정상의 검증**입니다. 실제 서버가 배포한 코드는 커밋 `6bc1076…`으로 고정했고, 모든 포트·네트워크 설정과 함께 코드로 남아 있습니다.”

### 답안 해설 — 동작 원리

| 요소 | 의미 |
|---|---|
| SSH 키 방식 | 공개키는 서버에, 개인키는 로컬에 보관 → 비밀번호가 네트워크를 타지 않아 안전. 개인키 재발급 불가이므로 저장소 밖에 보관하고 증거에도 내용을 기록하지 않음 |
| 포트 22 | 위 키를 사용하는 접속 통로 → SG가 개인 IP `/32`로만 허용 |
| `docker ps` | 실행 중 컨테이너 목록. `Up … (healthy)` |
| HEALTHCHECK | `wget -qO- http://127.0.0.1/health \| grep -qx 'OK'` — 30초 간격·3회 재시도 |
| 컨테이너 내부 확인 | 컨테이너는 독립 네트워크 → 내부 `127.0.0.1`은 컨테이너 자신. 외부 확인과 다른 층 |
| `cfn-signal` | UserData가 `/health` 확인 후 `success true/false` 신호 → `CreationPolicy`(15분)가 대기 |
| IMDSv2 | `HttpTokens: required` — 메타데이터 접근에 토큰 요구(자격 증명 탈취 방지) |

## 항목 1-③

> **문항**: 보안 그룹 인바운드가 “필요 포트만” 허용하며, SSH(22)가 특정 IP로 제한되어 있는가?

### 예상 답안 (구두)

> “인바운드 규칙은 **두 개가 전부**입니다. HTTP 80은 `0.0.0.0/0`, SSH 22는 제 개인 IP 하나(`/32`)에서만 허용합니다. 전체 포트(0-65535) 허용 규칙도, IPv6 인바운드도 없습니다. Security Group은 ‘연 것만 통과’시키는 구조라서 **이 두 줄이 곧 보안 방침**입니다. 아웃바운드는 패키지와 Docker 이미지를 받아야 해서 열어두었는데, SG가 상태를 기억하기 때문에 응답은 자동으로 허용되고 인바운드 노출과는 성격이 다릅니다. 그리고 실수 방지를 위해 템플릿에 SSH 전체 공개를 거부하는 규칙과 배포 스크립트 차단을 함께 넣었습니다.”

### 규칙표

| 방향 | 프로토콜 | 포트 | 소스 | 설명 |
|---|---|---|---|---|
| 인바운드 | TCP | 80 | `0.0.0.0/0` | Public HTTP |
| 인바운드 | TCP | 22 | 개인 IPv4 `/32` | SSH from learner public IP only |
| 아웃바운드 | 전체 | – | `0.0.0.0/0` | 패키지·이미지 다운로드 |

### 3중 안전장치

| # | 장치 | 동작 |
|---|---|---|
| 1 | 템플릿 `Rules.RejectPublicSsh` | `AllowedSshCidr = 0.0.0.0/0`이면 **스택 생성 거부** |
| 2 | 파라미터 `AllowedPattern` | `/32` 형식만 허용 |
| 3 | `scripts/deploy-stack.sh` | 전체 공개·root 배포·다른 스택/키 이름 차단 |

### 근거

| 구분 | 자료 |

## 항목 2-①

> **문항**: “외부 → IGW → Subnet → EC2”로 이어지는 네트워크 흐름을 다이어그램 기준으로 설명할 수 있는가?

### 예상 답안 (60초 대본)

> “사용자가 브라우저에서 공인 IP로 접속합니다. 요청은 인터넷을 지나 **Internet Gateway**를 통해 VPC로 들어옵니다. 다음으로 **퍼블릭 서브넷의 라우트 테이블**이 이 트래픽의 경로를 결정하고, 도착하기 전에 **Security Group이 80번 허용 여부**를 검사합니다. 통과하면 **EC2의 퍼블릭 IPv4**로 들어가고, 호스트의 80번 포트는 Docker가 게시한 **컨테이너 80번**으로 전달됩니다. 마지막으로 컨테이너 안의 **Nginx**가 요청을 받아 `index.html` 또는 `/health`를 응답합니다. 이 중 한 단계라도 빠지면 접속이 실패하므로, 장애가 발생하면 이 순서대로 외부에서 안쪽으로 확인합니다.”

### 다이어그램

```text
사용자 브라우저
   → 인터넷
   → Internet Gateway            (VPC 경계, 대문)
   → Public Subnet 라우트 테이블   (0.0.0.0/0 → IGW 안내판)
   → Security Group (TCP 80)      (현관 검문소)
   → EC2 퍼블릭 IPv4              (집 주소)
   → Docker 컨테이너 (80:80)      (응대 로봇)
   → Nginx → index.html / /health (안내 책자 · 내선 전화)
```

### “막히면 이렇게 보인다” 표 (항목4-①의 기초)

| 막힌 지점 | 증상 |
|---|---|
| IGW 미attach / 기본 경로 없음 | timeout (응답 없음) |
| SG 80 미허용 | timeout (패킷 폐기) |
| 퍼블릭 IP 없음 | 접속 불가 |
| 컨테이너/프로세스 중단 | connection refused (즉시 실패) |
| 콘텐츠 없음 | 404 |

**핵심 문장**: “timeout은 바깥(네트워크) 문제, refused·404는 안쪽(프로세스·콘텐츠) 문제.”

> “세 가지 기준을 사용했습니다. 첫째 **태그** — 모든 리소스에 `Project=b6-1`을 붙였고, CloudFormation이 붙이는 `aws:cloudformation:stack-name=b6-1-learning`도 함께 사용합니다. 둘째 **이름 규칙** — 스택 `b6-1-learning`, 키페어 `b6-1-key`, 보안 그룹 `b6-1-web-sg`처럼 `b6-1-` 접두어로 소유를 표시합니다. 셋째 **체크리스트** — `docs/cleanup-checklist.md`에 실제 리소스 ID를 기록하고 삭제 여부를 대조합니다. 특히 이 태그는 단순 표시가 아니라 **IAM 정책의 조건**으로도 사용되어, `Project=b6-1`과 스택 태그가 없으면 변경·삭제 권한 자체가 없습니다. 스택이 삭제되어도 남는 키페어 같은 리소스는 별도로 추적했습니다.”

# 제3장 항목 3 — 이해 심화

## 항목 3-①

> **문항**: Public Subnet Route Table의 기본 경로(`0.0.0.0/0` → IGW)가 필요한 이유를 설명할 수 있는가?

### 예상 답안 (구두)

> “서브넷 안의 EC2는 사설 IP `10.0.1.x`를 사용합니다. 외부의 임의 목적지로 나가는 트래픽은 라우트 테이블이 경로를 결정하는데, 모든 목적지에 대한 개별 경로가 있는 것이 아닙니다. 그래서 **표에 없는 모든 목적지를 뜻하는 `0.0.0.0/0` 기본 경로**가 필요하고, 그 대상을 Internet Gateway로 지정해야 VPC 밖으로 나갈 수 있습니다. 이 경로가 없으면 요청이 도착해도 **응답을 되돌려 보낼 수 없어** 접속이 실패로 보입니다. 여기에 IGW가 VPC에 연결되어 있고 인스턴스에 퍼블릭 IPv4가 있어야 하며, 이 세 조건이 함께 성립해야 ‘퍼블릭’이 됩니다.”

### 동작 원리

| 요소 | 없으면 |
|---|---|
| 기본 경로 `0.0.0.0/0 → IGW` | 나가는 길·응답 경로 없음 → timeout |
| IGW attach | 인터넷 진입 불가 |
| 퍼블릭 IPv4 | 주소 부재 → 접속 불가 |

- “퍼블릭 서브넷”은 설정 플래그가 아니라 **위 세 조건이 만드는 결과**다.
- 내부 통신은 `10.0.0.0/16 → local` 자동 경로로 별개 동작한다.

### 연계 질문

| 예상 질문 | 답변 |
|---|---|
| 라우트만 있으면 되나? | “아닙니다. IGW attach + 퍼블릭 IPv4 + SG 허용까지 필요합니다. 장애 점검 순서가 이 세 가지를 확인합니다.” |
| 왜 하필 `0.0.0.0/0`인가? | “개별 목적지 경로를 다 만들 수 없으므로 ‘나머지 전부’를 처리하는 기본 경로가 필요합니다.” |
| 더 구체적인 경로가 있으면? | “라우터는 더 구체적인 경로를 우선합니다. VPC 내부 통신은 `local` 경로가 우선 적용됩니다.” |

## 항목 3-②

> **문항**: Security Group과 IAM의 책임 범위 차이를 설명하고, “최소 권한”이 왜 필요한지 설명할 수 있는가?

### 예상 답안 (구두)

> “Security Group은 **네트워크 계층**에서 인스턴스 앞으로 오가는 패킷을 검사합니다. IAM은 **컨트롤 플레인**에서 사람이나 프로그램이 AWS API를 호출할 권한을 결정합니다. 층이 다르기 때문에 SG에서 80번을 열어도 AWS를 조작할 권한이 생기지 않고, 반대로 IAM 권한이 넓어도 네트워크가 막혀 있으면 서버에 접속할 수 없습니다. 최소 권한이 필요한 이유는 **사고 반경을 줄이기 위해서**입니다. 저는 두 개의 제한 정책을 사용했고, 조건으로 서울 리전, 정확한 스택 이름, 태그, 인스턴스 타입 `t3.micro`, IMDSv2, 암호화 gp3 8GiB 이하, 키페어 `b6-1-key`를 요구했습니다. 그 결과 실수로도 다른 VPC에 리소스를 만들거나 큰 인스턴스를 만들 수 없습니다. 권한이 부족할 때는 관리자 권한을 추가하지 않고, 거부된 작업·대상·조건을 확인해 필요한 문장만 좁혀서 추가합니다.”

### 책임 범위 비교

| 구분 | Security Group | IAM |
|---|---|---|
| 층 | 네트워크(데이터 플레인) | 관리(컨트롤 플레인) |
| 대상 | 패킷 | AWS API 호출 |
| 붙는 대상 | 인스턴스(ENI) | 사용자·역할 |
| 결과 | 트래픽 통과/차단 | 호출 허용/거부 |
| 무력화 조건 | – | 네트워크가 막히면 접속 불가 |

### 우리 정책 구성
`B61DeployerPolicyRestricted`(스택 관리) + `B61Ec2DeploymentPolicy`(CloudFormation 경유 EC2 작업) + `IAMUserChangePassword`. IAM 관리·액세스 키 발급·`PassRole` 권한은 부여하지 않았다.

### 근거
`docs/deployment-permissions.md`, `23-iam-policy-key-dryrun.*`, `20-minimum-permissions-prepared.*`, `31-billing-readonly-fixed.*`

### 연계 질문

| 예상 질문 | 답변 |
|---|---|
| SG만 잘하면 되나? | “아닙니다. 층이 다르므로 둘 다 최소화해야 합니다. 실제 이번 실습에서 발생한 실패 3건은 모두 IAM 쪽이었습니다.” |
| 최소 권한의 대가는? | “작업 실패가 잦아집니다. 그래서 거부 메시지를 근거로 범위를 좁히는 절차를 문서화해 두었습니다.” |
| 왜 조건을 그렇게 많이 걸었나? | “ARN을 미리 알 수 없는 생성 작업의 범위를 요청 속성(태그·타입·암호화)으로 제한하기 위해서입니다.” |

## 항목 3-③

> **문항**: SSH(22) 또는 DB 포트를 `0.0.0.0/0`로 열면 안 되는 이유와 대안을 설명할 수 있는가?

### 예상 답안 (구두)

> “인터넷 전체에 관리 포트를 열면 **스캔과 브루트포스 시도의 즉각적인 대상**이 됩니다. SSH는 하루에도 수천 건의 로그인 시도가 들어오는 것이 일반적이고, DB 포트는 자격 증명 탈취 시 데이터 유출로 직결됩니다. 또한 관리 포트를 임시로 열어두고 잊는 사고가 흔하기 때문에 과제 제약 사항에도 SSH 소스 제한이 명시되어 있습니다. 대안으로는 ① 내 IP `/32`로 제한, ② 포트를 아예 열지 않는 **SSM Session Manager**, ③ Bastion을 두더라도 관리 대역만 허용, ④ 앱 계층과 DB 간 **SG 참조**, ⑤ VPC 내부 통신 유지, ⑥ 필요 시 VPN·피어링이 있습니다. 저는 ①을 적용하고 임시 개방 규칙은 즉시 제거했습니다.”

### 위험과 대안

| 위험 | 설명 |
|---|---|
| 스캔·색인 | 열린 포트는 수 분 내 탐지되어 목록화됨 |
| 브루트포스 | 자동 로그인 시도가 상시 유입 |
| 자격 증명 탈취 | DB 직결 시 데이터 유출 |
| 방치 | “임시”로 연 규칙이 영구화 |

| 대안 | 원리 |
|---|---|
| 내 IP `/32` | 사원증 있는 사람만 |
| SSM Session Manager | 에이전트가 밖으로 연결 → **인바운드 포트 불필요** |
| Bastion + 관리 대역 | 경유지 하나만 최소 허용 |
| SG-to-SG 참조 | 앱 SG만 DB SG 접근 허용 |
| 프라이빗 서브넷 | 인터넷 경로 자체를 미부여 |
| VPN / 피어링 | 사설 경로로 접근 |

# 제4장 항목 4 — 응용·장애 대응

## 항목 4-①

> **문항**: 외부 접속이 안 될 때, 어떤 순서(라우팅 → SG → 퍼블릭 IP/DNS → 서버 프로세스/로그)로 점검하는지 설명할 수 있는가?

### 예상 답안 (구두)

> “**바깥에서 안쪽으로, 싼 것부터** 확인합니다. 먼저 CloudFormation 이벤트로 배포 자체의 실패가 없는지 봅니다. 그다음 ① **라우팅** — 라우트 테이블에 `0.0.0.0/0 → IGW`가 있는지, IGW가 VPC에 연결되어 있는지 확인합니다. ② ** Security Group** — 80이 허용되고 소스가 맞는지, 서브넷 네트워크 ACL이 막고 있지 않은지 봅니다. ③ **주소** — 인스턴스에 퍼블릭 IPv4가 있는지, 도메인을 사용한다면 DNS가 그 주소를 가리키는지 확인합니다. ④ 여기까지 정상이면 서버에 들어가 **프로세스**를 봅니다 — `docker ps -a`, 내부 `curl localhost/health`, 포트 리슨 상태입니다. ⑤ 마지막으로 **로그**입니다 — `docker logs`, Nginx access/error 로그, 부팅 로그(`cloud-init-output`)를 확인합니다. 증상으로도 좁힐 수 있어서, timeout은 바깥 문제, connection refused나 404는 안쪽 문제로 판단합니다.”

### 점검표

| 순서 | 확인 항목 | 방법 | 단서 |
|---|---|---|---|
| 0 | 배포 상태 | CloudFormation 이벤트 | 생성 실패면 즉시 종료 |
| 1 | 라우팅 | RT `0.0.0.0/0`→IGW, IGW attach | timeout |
| 2 | SG·ACL | 80 인바운드·소스 | timeout |
| 3 | 주소 | 퍼블릭 IPv4, DNS | 접속 불가 |
| 4 | 프로세스 | `docker ps -a`, 내부 `/health`, 포트 | refused |
| 5 | 로그 | `docker logs`, Nginx log, cloud-init | 404/502 |

### 근거
`docs/troubleshooting.md`의 “AWS 문제 확인 순서” 9단계, `04`~`08`, `31`~`33`

### 연계 질문

| 예상 질문 | 답변 |
|---|---|

## 항목 4-②

> **문항**: IAM 권한이 부족해 작업이 실패했다면, “권한을 무작정 올리지 않고” 어떤 방식으로 필요한 최소 범위를 찾아갔는지 설명할 수 있는가?

### 예상 답안 (구두)

> “다섯 단계로 진행했습니다. ① 오류 메시지에서 **거부된 API와 리전**을 확인합니다. ② 그 작업이 대상으로 하는 **리소스 ARN을 특정**합니다. ③ 리소스가 아직 없어 ARN을 알 수 없는 생성 작업이면 **조건으로 범위를 제한**합니다 — 태그 `Project=b6-1`, 인스턴스 타입, 암호화 여부 등입니다. ④ 그 범위만 허용하는 문장을 추가하고 **IAM Access Analyzer로 검증**합니다. ⑤ dry-run·시뮬레이터·실제 재시도로 허용과 거부를 다시 확인합니다. 이 방식으로 시작 템플릿 권한, 네트워크 태그 갱신, 정리 단계 삭제 권한을 해결했습니다. `AdministratorAccess` 같은 넓은 권한은 사용하지 않았습니다.”

### 5단계 표

| 단계 | 내용 | 도구 |
|---|---|---|
| 1 | 거부된 API·리전 확인 | 오류 메시지(“no identity-based policy allows…”) |
| 2 | 대상 리소스 ARN 특정 | 리소스 ID·스택 ARN |
| 3 | 생성 작업은 **조건**으로 제한 | 태그·타입·암호화 조건 |
| 4 | 최소 문장 추가 + 검증 | Access Analyzer |
| 5 | 재검증 | dry-run, 시뮬레이터, 실제 재시도 |

**관리자 권한이 최악인 이유**: ① 사고 반경 확대 ② 무엇이 필요했는지 알 수 없게 되어 **재현·설명 불가**.

## 항목 4-③

> **문항**: 트래픽이 늘어 “인스턴스를 2대로 늘려라” 한다면, 현재 구조에서 무엇이 병목이고 어떤 구성 요소(ALB 등)를 추가할지 설명할 수 있는가?

### 예상 답안 (구두)

> “현재 구조의 병목은 세 가지입니다. 첫째, **인스턴스가 1대라 단일 장애점**이라는 점입니다. 둘째, **서브넷이 가용영역 한 곳에만 있어 다중 AZ 구성이 불가능**합니다. 셋째, **공인 주소가 인스턴스에 직접 붙어 있어 교체·확장이 경직**됩니다. 2대로 늘리려면 ① 서로 다른 가용영역에 **서브넷 2개 이상**, ② **ALB와 타깃 그룹**(헬스체크 경로는 기존 `/health` 재사용), ③ **Auto Scaling 그룹**이 필요합니다. 그리고 구조를 바꿔서 **공인 트래픽은 ALB만 받고 EC2는 ALB의 보안 그룹에서만 80을 허용**하도록 해야 합니다. 이 사이트는 정적이어서 세션 상태가 없기 때문에 수평 확장이 단순하고, 대가는 ALB 비용과 구성 복잡도입니다.”

### 병목 3개

| # | 병목 | 영향 |
|---|---|---|
| 1 | 인스턴스 1대 | 단일 장애점 |
| 2 | 서브넷 1개(AZ 1곳) | 다중 AZ 불가 |
| 3 | 공인 IP 인스턴스 직결 | 교체·확장 경직 |

### 추가 구성 4개

| 추가 | 목적 |
|---|---|
| AZ별 서브넷 2개 이상 | 한 AZ 장애에도 서비스 유지 |
| ALB + 타깃 그룹 | 부하 분산 + **헬스체크로 죽은 대상 자동 제외**(`/health` 재사용) |
| Auto Scaling 그룹 | 인스턴스 수·교체 자동화 |
| SG 재구성 | 공인은 ALB만, EC2는 ALB SG에서만 80 허용 |

```text
        인터넷
          │
       [ ALB ]   ← 공인 주소는 ALB에만 (80/443)
       ┌───┴───┐
  [EC2 #1]  [EC2 #2]   ← 서로 다른 AZ, 80은 ALB SG에서만
   (AZ-a)    (AZ-c)
```

| 예상 질문 | 답변 |
