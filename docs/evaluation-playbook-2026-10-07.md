> **읽는 방법**: 문항이 물어보는 것은 3가지다 — **(가) 어떻게 설명할지, (나) 무엇을 보여줄지, (다) 이어서 올 질문에 뭘 답할지.** 그리고 그 답이 바로 **내가 지금 해야 할 일**로 이어진다.

## 0. 항목 연결 지도 — 어디서 어디로 이어지는가

```text
[항목1 실물]                 [항목2 설명]              [항목3 이해]                 [항목4 응용]
1-① VPC·IGW·라우팅   →   2-① 흐름 설명       →   3-① 기본 경로가 필요한 이유   →   4-① 장애 점검 순서
1-③ SG 최소 허용      →   2-② 최소화 기준      →   3-② SG vs IAM / 최소 권한    →   4-② IAM 최소 범위 찾기
                                                     3-③ SSH·DB 개방 위험·대안
1-④ A/B 외부 접속     →   2-③ 선택 근거·구성
1-⑤ 정리 완료         →   2-④ 추적 기준        →                                →   4-④ Billing 추적·정리
1-② SSH·서버 실행     →                       →   3-④ 트러블슈팅 가설→검증     →   4-① / 4-②
                                                     4-③ 2대 확장(ALB)
```

**핵심 3가지 연결**

1. **네트워크 사슬(1-① → 2-① → 3-① → 4-①)**: "한 단계라도 빠지면 접속 실패"가 전부 같은 논리다. 1-①에서 보여준 구성이 2-①의 그림이고, 3-①의 "왜"이고, 4-①의 점검 순서다.
2. **보안 사슬(1-③ → 2-② → 3-②·③ → 4-②)**: SG(패킷)와 IAM(API)은 층이 다르다. 이 한 문장이 4개 문항에 반복된다.
3. **정리 사슬(1-⑤ → 2-④ → 4-④)**: 태그·이름 규칙·체크리스트가 추적이고, 그 추적이 비용 사고를 막는다.

**→ 그래서 답변은 항목별로 따로 외우지 말고, 위 3개 사슬로 묶어서 기억하는 것이 효율적이다.**

## 2. 항목 1 — 실물 확인 (PASS/FAIL)

### 1-① VPC·Public Subnet·IGW·Route Table(`0.0.0.0/0`→IGW) 구성

**어떻게 설명할지 — 말하는 순서 3단:**
1. “리소스 3개를 만들었습니다: VPC `10.0.0.0/16`, 그 안 퍼블릭 서브넷 `10.0.1.0/24`, Internet Gateway.”
2. “IGW는 **VPC에 attach**했고, 서브넷의 라우트 테이블 `b6-1-public-rt`에 **기본 경로 0.0.0.0/0 → IGW**를 넣었습니다.”
3. “라우트 테이블은 **서브넷에 association**까지 했고, 서브넷은 퍼블릭 IPv4 자동 할당이 켜져 있습니다. EC2의 퍼블릭 IPv4와 함께 이 세 조건이 성립해야 인터넷에서 접속됩니다.”

**무엇을 보여줄지:**
- (라이브) VPC 콘솔 → **라우팅 테이블** → `b6-1-public-rt` → **경로 탭**(`0.0.0.0/0 → igw-…`) + **서브넷 연결 탭**(`b6-1-public-subnet`)
- (증거) `evidence/2026-10-03/10-ebs-vpc-route.txt`, `18-network-ebs-reaudit.txt`, `27-iam-network-health.txt`
- (그림) `docs/architecture.svg`

**연계 질문 → 답:**
| 예상 질문 | 답 |
|---|---|
| “IGW가 뭘 하는 장치인가?” | “VPC 경계에서 사설 IP와 인터넷을 연결하는 출입구입니다. NAT처럼 주소를 변환하는 게 아니라 1:1이라서 인스턴스에 퍼블릭 IPv4가 따로 필요합니다.” |
| “프라이빗 서브넷은 없나?” | “과제 최소 구성이 퍼블릭 1개이고 EC2가 인터넷에 직접 공개되어야 하는 구조라서 퍼블릭만 뒀습니다. 계층 분리가 필요하면 프라이빗+NAT가 추가됩니다.” |
| “라우팅 테이블은 서브넷마다 필요한가?” | “서브넷은 라우트 테이블 하나에 연결됩니다. 지금은 공용 1개를 모든(1개) 서브넷이 공유합니다.” |
| “가용영역은?” | “서브넷은 `GetAZs`의 첫 번째 AZ 한 곳입니다. 다중 AZ는 4-③ 확장 시나리오에서 설명합니다.” |

**내가 할 일:** 재배포 시 라우트 테이블 화면을 캡처해 `evidence/2026-10-XX/`에 남기고, 콘솔 탭을 1-①→1-③ 순서로 미리 열어둔다.

**어떻게 설명할지 — 3단:**

**무엇을 보여줄지:**
- (라이브) 터미널: `docker ps --format 'table {{.Names}}\t{{.Status}}'` → healthy / `docker exec b6-1-web curl -s -o /dev/null -w '%{http_code}' localhost/health`

**연계 질문 → 답:**
| 예상 질문 | 답 |
|---|---|
| “왜 t3.micro인가?” | “과제가 프리 티어 micro급 1대를 지정했고, 템플릿도 `AllowedValues: [t3.micro]`로 잠가서 다른 타입이 아예 생성되지 않습니다.” |

### 1-③ SG 인바운드 “필요 포트만” + SSH(22) 특정 IP 제한

**어떻게 설명할지 — 3단:**
1. “인바운드 규칙은 **2개가 전부**입니다. HTTP 80은 `0.0.0.0/0`, SSH 22는 **제 개인 IP `/32`** 하나.”
2. “전체 포트(0-65535) 규칙도, IPv6 인바운드도 없습니다. 아웃바운드는 패키지·이미지 다운로드용으로 열어뒀는데 인바운드 노출과는 방향이 다릅니다.”
3. “게다가 템플릿에 **SSH 0.0.0.0/0을 거부하는 Rule**(`RejectPublicSsh`)과 배포 스크립트 차단이 있어서 실수로도 전체 공개가 안 됩니다.”

**무엇을 보여줄지:**
- (라이브) EC2 → 인스턴스 → **보안 탭** → SG → **인바운드 규칙 “전체 보기”** (규칙 2개가 한눈에)
- (증거) `09-iam-ec2-security-group.jpg/txt`, `18-network-ebs-reaudit.txt`, `27-iam-network-health.txt`
- (코드) `infra/cloudformation.yml`의 `WebSecurityGroup`·`Rules.RejectPublicSsh` — “정책이 아니라 코드로 강제된다”를 보여주는 카드

**연계 질문 → 답:**
| 예상 질문 | 답 |
|---|---|
| “집 IP가 바뀌면?” | “SSH가 막힙니다. 이때 SG를 전체로 여는 게 아니라 소스를 갱신하거나, 무포트 접속(SSM Session Manager)으로 전환하는 게 맞습니다.” |
| “그럼 22번은 닫아도 되나?” | “SSM을 쓰면 가능합니다. 다만 과제가 SSH 접속을 요구해서 내 IP `/32`로 열어 관리했습니다.” |
| “DB 포트는?” | “DB를 만들지 않아서 열지 않았습니다. 만들었더라도 전체 공개 대신 SG 참조/프라이빗 서브넷만 허용합니다.” |
| “아웃바운드 전체 허용은 안전한가?” | “인스턴스가 이미지·패키지를 받아야 해서 필요했고, 인바운드와 달리 외부에서 들어오는 경로가 아닙니다. 최소화 원칙의 우선 대상은 인바운드입니다.” |

**내가 할 일:** 캡처에 나타나는 **개인 IP 가림본**을 만들어 둔다(공개 제출용). “규칙 2개”라는 숫자를 즉답으로 말할 수 있게 연습.

## 4. 항목 3 — 이해 심화 (PASS/FAIL)

### 3-① 기본 경로(`0.0.0.0/0`→IGW)가 필요한 이유

**대본:** “EC2는 사설 IP를 씁니다. 목적지별 경로가 다 있는 게 아니므로 기본 경로가 없으면 **밖으로 나갈 수도, 응답을 돌려받을 수도 없습니다.** 그래서 서브넷 라우트 테이블의 `0.0.0.0/0`을 IGW로 보냅니다. 여기에 IGW attach와 퍼블릭 IPv4까지 성립해야 ‘퍼블릭’이 됩니다.”

**연계 질문:** “라우트만 있으면 되나?” → “아닙니다. IGW attach + 퍼블릭 IPv4 + SG 허용이 모두 필요합니다. 4-① 점검 순서가 이 세 가지를 확인합니다.”

### 3-② SG vs IAM + 최소 권한이 왜 필요한가

**대본:** “SG는 **네트워크 계층**에서 인스턴스 앞 패킷을 거르고, IAM은 **컨트롤 플레인**에서 사람/프로그램의 AWS API 호출 권한을 정합니다. 층이 달라서 SG로 80을 열어도 AWS 조작 권한이 생기지 않고, IAM이 넓어도 네트워크가 막히면 못 들어옵니다. 최소 권한은 사고 반경을 줄이는 장치입니다. 실제로는 두 정책에 서울 리전·스택 이름·태그·`t3.micro`·IMDSv2·암호화 gp3 8GiB·키 `b6-1-key` 조건을 걸어, 실수로도 다른 VPC나 큰 인스턴스가 생기지 않게 했습니다. 권한이 부족하면 관리자 권한을 붙이지 않고 거부된 작업·대상만 확인해 문장을 좁혀 추가합니다.”

**연계 질문:** “그럼 SG만 잘하면 되나?” → “아닙니다. SG는 트래픽, IAM은 관리 권한이라 둘 다 최소화해야 합니다. 실제로 이번 실습의 실패 3건은 전부 IAM이었습니다.”

### 3-③ SSH/DB를 `0.0.0.0/0`으로 열면 안 되는 이유와 대안

**대본:** “인터넷 전체 공개는 즉시 스캔·브루트포스 대상이 됩니다. SSH는 초당 수천 건의 로그인 시도가 일상이고, DB 포트는 자격 증명 탈취 시 데이터 유출로 직결됩니다. 또 관리 포트를 임시로 열고 잊는 사고가 흔해서 과제 제약에도 SSH 소스 제한이 명시되어 있습니다. 대안은 ① 내 IP `/32`, ② SSM Session Manager(무포트), ③ Bastion은 관리 대역만, ④ SG-to-SG 참조, ⑤ VPC 내부 통신 유지입니다.”

**연계 질문:** “포트 번호를 바꾸면 되나?” → “아닙니다. 회피일 뿐이고 스캔으로 다시 발견됩니다. 소스 제한이 실질적인 방어입니다.”

### 3-④ 가설→검증 순서를 지킨 이유 + 로그·근거 활용

**대본:** “동시에 여러 개를 고치면 원인을 특정할 수 없고 재현도 안 됩니다. 그래서 증상 → 가설 → 검증 → 조치 → 결과 → 재발 방지 순서를 지켰습니다. 실제 3건: 시작 템플릿 권한(`04`)→오류로 거부 API 확인→범위를 좁혀 수정(`05`), 네트워크 태그 갱신(`06`)→태그 조회·정책 검증(`07·08`), 정리 중 삭제 거부(`37·40`)→정확한 리소스 권한 추가(`42`)→재시도 성공(`43`). 활용 근거는 CloudFormation 이벤트, IAM dry-run 오류, `docker logs`, `/var/log/cloud-init-output.log`입니다.”

## 부록 C — 1-① 용어 해설: attach · route · association (3가지 다른 동작)

### C-1. 한 문장을 세 동작으로 쪼개기

> “**IGW를 VPC에 attach**하고, **서브넷의 라우트 테이블에 `0.0.0.0/0` → IGW 기본 경로를 넣었습니다.**”

| # | 하는 일 | 비유(건물 단지) | AWS 리소스 | 없으면 |
|---|---|---|---|---|
| ① | IGW를 **VPC에 연결(attach)** | 단지에 **정문을 세우고 울타리에 연결** | `InternetGatewayAttachment` (`AWS::EC2::VPCGatewayAttachment`) | 정문이 연결되지 않아 인터넷으로 나갈 수 없음. 경로를 IGW로 만들려 해도 AWS가 “같은 VPC 소속이 아니다”라며 거부 |
| ② | 라우트 테이블에 **경로 규칙 추가(route)** | 각 동에 붙은 **안내판에 한 줄 적기** — “여기 없는 모든 목적지 → 정문” | `DefaultPublicRoute` (`AWS::EC2::Route`, `DestinationCidrBlock: 0.0.0.0/0`, `GatewayId: IGW`) | 정문은 있는데 나가는 길을 몰라 인터넷 불가. **인바운드 요청이 도착해도 응답(출발)이 막혀** 브라우저는 응답 시간 초과 |
| ③ | **라우트 테이블을 서브넷에 연결(association)** | 어느 동이 **어느 안내판을 쓸지** 지정 | `PublicSubnetRouteTableAssociation` (`AWS::EC2::SubnetRouteTableAssociation`) | 서브넷이 VPC 기본 라우트 테이블을 쓰게 되어, 만든 안내판(경로)이 적용되지 않음 |

**핵심**: ①은 **VPC 전체**에 대한 한 번의 연결, ②③은 **서브넷별**로 달라질 수 있는 설정이다. 그래서 세 동작이 분리되어 있고, **셋 다 있어야** “공인 IP를 가진 EC2가 인터넷과 양방향 통신”이 된다.

### C-2. `0.0.0.0/0`이 무슨 주소인가

- CIDR에서 `/0`은 “앞 **0비트**만 고정”이라는 뜻 → **모든 IPv4 주소**를 의미한다. 즉 “어딘가 정해진 곳”이 아니라 **“표에 따로 적히지 않은 모든 목적지”** 다.
- 비교: `10.0.0.0/16` = 앞 16비트 고정 → `10.0.x.x`만.
- 그래서 `0.0.0.0/0`을 가리켜 **기본 경로(default route)** 라고 부른다. “마지막에 쓰는 규칙”, “나머지 전부”라는 뜻.
- 라우터(VPC 라우터)는 **더 구체적인 경로를 우선**한다. 예: VPC 내부 통신 `10.0.0.0/16 → local`은 자동으로 들어 있고, 그 밖의 목적지만 `0.0.0.0/0 → IGW`를 탄다.

### C-3. 우리 템플릿 실제 코드

```yaml
  InternetGateway:                       # ① 정문을 세움
    Type: AWS::EC2::InternetGateway
  InternetGatewayAttachment:             # ① 정문을 단지(VPC)에 연결  ← attach
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: {Ref: Vpc}
      InternetGatewayId: {Ref: InternetGateway}
  PublicRouteTable:                      # ② 안내판
    Type: AWS::EC2::RouteTable
    Properties:
      VpcId: {Ref: Vpc}
  DefaultPublicRoute:                    # ② 안내판에 한 줄: 모든 목적지 → 정문
    Type: AWS::EC2::Route
    DependsOn: InternetGatewayAttachment #   순서 강제: attach가 끝나야 경로를 만든다
    Properties:
      RouteTableId: {Ref: PublicRouteTable}
      DestinationCidrBlock: 0.0.0.0/0
      GatewayId: {Ref: InternetGateway}
  PublicSubnetRouteTableAssociation:     # ③ 이 안내판을 서브넷에 붙임
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: {Ref: PublicSubnet}
      RouteTableId: {Ref: PublicRouteTable}
```

### C-4. “서브넷이 퍼블릭”의 정의

서브넷에 `public`이라는 플래그가 따로 있는 게 **아니다.** 다음이 성립하면 그 서브넷은 퍼블릭이다.

1. 라우트 테이블에 `0.0.0.0/0 → IGW` 경로가 있고,
2. 그 IGW가 VPC에 attach되어 있고,
3. 인스턴스에 퍼블릭 IPv4가 부여되어 있다(우리는 `MapPublicIpOnLaunch: true` + `AssociatePublicIpAddress: true`).

→ **2번과 3번이 `1-①`·`3-①` 답변의 뼈대**이고, 하나라도 빠지면 “퍼블릭인데 인터넷이 안 되는” 상태가 된다.

### C-5. 콘솔·CLI에서 확인하는 방법

- 콘솔: VPC → **라우팅 테이블** → `b6-1-public-rt` → **경로 탭**에서 `0.0.0.0/0 → igw-…`, **서브넷 연결 탭**에서 `b6-1-public-subnet` / VPC → 인터넷 게이트웨이에서 **상태 `Attached`**.
- CLI:
  ```bash
  aws ec2 describe-route-tables --region ap-northeast-2 \
    --filters "Name=association.subnet-id,Values=<SubnetId>" \
    --query "RouteTables[0].Routes"
  aws ec2 describe-internet-gateways --region ap-northeast-2 \
    --query "InternetGateways[].Attachments"
  ```
- `scripts/aws-verify.sh`의 `route_0.0.0.0/0_to_igw=PASS` 줄이 **이 ①②를 검사한 결과**다.

### C-6. 평가에서 이렇게 말한다 (쉬운 버전)

> “Internet Gateway를 만들어서 **VPC에 연결(attach)**했습니다. 그리고 퍼블릭 서브넷이 쓰는 라우트 테이블에 **‘목적지 0.0.0.0/0, 즉 표에 없는 모든 목적지는 IGW로 보낸다’는 기본 경로**를 추가했고, 그 라우트 테이블을 **서브넷에 연결**했습니다. 연결(attach)과 경로(route)는 다른 작업이고, 둘 다 있어야 서브넷이 퍼블릭이 됩니다. 콘솔 경로 탭에서 `0.0.0.0/0 → igw-…`로 보입니다.”

### C-7. 꼬리질문 대비

| 질문 | 답 |
|---|---|
| “IGW 만들면 자동으로 붙나?” | “아닙니다. 만드는 것과 VPC에 연결(attach)하는 것은 별개 리소스입니다.” |
| “attach만 하고 경로는 안 넣으면?” | “나가는 길을 모르니 인터넷이 안 됩니다. 인바운드가 와도 응답을 못 내보내 접속이 실패합니다.” |
| “왜 경로를 IGW가 아니라 라우트 테이블에 넣나?” | “경로 정보는 라우트 테이블이 들고 있고, 서브넷은 라우트 테이블과 연결되어 그 정보를 씁니다. 서브넷별로 다른 라우팅을 주려고 분리되어 있습니다.” |
| “VPC 안에서 통신도 되나?” | “됩니다. `10.0.0.0/16 → local` 경로가 자동으로 있어서, attach·기본 경로와 무관하게 VPC 내부 통신은 성립합니다.” |
| “`0.0.0.0/0`은 IPv6도 포함하나?” | “아닙니다. IPv6는 `::/0`으로 따로 씁니다. 우리 VPC는 IPv6를 쓰지 않습니다.” |
