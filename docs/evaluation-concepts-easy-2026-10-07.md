| Billing | **관리비 명세서** |

**공통 원리 3개 — 모든 문항의 바탕**

1. **기본은 거부** — 대문·현관 모두 닫혀 있고, “연 것만” 통한다(허용 목록 모델).
2. **층이 다르면 장치도 다르다** — 현관 검문소(SG)와 권한 카드(IAM)는 완전히 다른 층. 하나를 잘해도 다른 하나가 뚫려 있으면 소용없다.
3. **증거가 없으면 없었던 일** — 이름표(태그)와 반납 목록(체크리스트)이 없으면 정리했어도 정리한 게 아니다.

# 항목 1 — 실물 확인 (쉬운 해설)

> 1-①(VPC·IGW·라우팅)은 플레이북 **부록 C**에 이미 자세히 있으므로 여기서는 생략한다.

## 1-② SSH로 접속되고, 웹 서버가 실행 중인가?

**① 뜻**: ① 내가 인터넷 건너편 컴퓨터에 **원격으로 들어가 명령을 칠 수 있고**, ② 그 컴퓨터 안에서 **웹사이트가 살아서 돌고 있는지**.

**② 비유**: ①은 **리모컨 + 현관 열쇠**로 집에 들어가기, ②는 들어가 보니 **응대 로봇이 콘센트에 꽂혀 대기 중인지** 확인하는 것.

**③ 실제 동작 (우리 것)**

- **SSH 열쇠 방식**: EC2를 만들 때 “키페어”를 지정하면 **자물쇠(공개키)**는 서버에 설치되고 **열쇠(개인키)**는 내 PC에 남는다. 접속할 때 개인키로 서명하면 서버가 공개키로 검증한다 → **비밀번호가 네트워크를 타지 않아 안전**하다. 개인키는 재발급이 안 되므로 저장소 밖에 보관하고, 내용을 증거에 기록하지 않는다.
- **포트 22**가 그 열쇠 구멍이고, 그래서 SG가 22를 내 IP로만 열어둔 것이다.
- **`docker ps`**: 실행 중인 컨테이너 목록. 우리 것은 `b6-1-web` 하나, 상태가 `Up … (healthy)`.
- **healthy가 어디서 나오나**: Docker가 직접 검사한다. `Dockerfile`의 `HEALTHCHECK --interval=30s --timeout=3s --retries=3 CMD wget -qO- http://127.0.0.1/health | grep -qx 'OK'` — 즉 **로봇에게 30초마다 내선 전화를 걸어 “OK”라고 답하는지** 확인한다. 3번 실패하면 `unhealthy`.
- **왜 컨테이너 “안에서” 확인하나**: 컨테이너는 자기만의 네트워크를 가진 작은 방이라, 그 방 안의 `127.0.0.1`은 로봇 자신이다. 밖에서 확인하는 것과 안에서 확인하는 것은 다른 층이다.
- **`cfn-signal`**: 준비가 끝난 로봇이 **본사(CloudFormation)에 “완료” 전화**를 하는 장치. 템플릿의 `CreationPolicy`(15분)가 그 전화를 기다리고, UserData는 `/health`가 OK가 되면 `success true`, 30번 재시도에도 안 되면 `success false`로 전화한 뒤 실패로 끝낸다.
  → **그래서 “스택 완료 = 서비스 정상”이 기계적으로 보장된다.** 비유: 이삿짐 검수 완료 도장이 찍힌 것.
- 배포 코드는 커밋 `6bc1076c4311…`으로 고정, IMDSv2 필수(서버 메타데이터에 인증 토큰을 요구해 탈취 공격을 막는 옵션), Amazon Linux 2023 `t3.micro`.

**④ 평가에서 이렇게 말한다**

> “SSH로 접속하면 Amazon Linux 2023 `t3.micro`가 보입니다. `docker ps`에는 `b6-1-web` 컨테이너가 healthy로 떠 있고, 컨테이너 안에서 `curl localhost/health`를 치면 200과 `OK`가 나옵니다. healthy는 Docker가 30초마다 `/health`로 검사한 결과입니다. 그리고 배포는 준비 완료 신호(`cfn-signal`)를 받아야 스택이 완료되게 만들어서, **스택이 완료 상태라는 것 자체가 서비스 정상의 증거**입니다. 서버가 돌린 코드는 커밋으로 고정했습니다.”

**⑤ 꼬리질문 대비**

| 질문 | 답 |
|---|---|
| “개인키를 잃으면?” | “재발급이 불가능합니다. 그래서 저장소 밖에 보관하고 증거에도 내용을 남기지 않았습니다.” |
| “왜 비밀번호가 아니라 키인가?” | “비밀번호는 전송·재사용 위험이 있어서, 공개키 인증이 기본입니다.” |
| “IMDSv2는 왜?” | “인스턴스 메타데이터 접근에 토큰을 요구해, SSRF 같은 취약점으로 자격 증명이 새는 것을 막습니다.” |

## 1-③ 보안 그룹이 “필요 포트만”, SSH(22)는 특정 IP만

**① 뜻**: 현관 검문소의 **허용 목록**을 보여주고, “연 것 2개 말고는 없다”를 증명하는 것.

**② 비유**: 건물 출입문이 딱 두 개 — **정문(80)**: 누구나 / **관리자문(22)**: 내 사원증 번호(`/32`)를 가진 사람만. 나머지 문은 벽으로 막아놨다.

**③ 실제 동작**

- **허용 목록 모델**: SG는 “금지 목록”이 아니라 **연 것만 통과**시킨다(기본 전부 차단). 그래서 SG 화면의 규칙 목록 = **우리 보안 방침 그 자체**다.
- **`/32`, `/0` 뜻**: 앞 숫자는 “고정하는 비트 수”.
  | 표기 | 뜻 |
  |---|---|
  | `0.0.0.0/0` | 고정 0비트 = **모든 IPv4 주소** (= 세상 전부) |
  | `10.0.1.0/24` | 앞 24비트 고정 = `10.0.1.x` 256개 |
  | `203.0.113.7/32` | 앞 32비트 고정 = **딱 하나의 주소** |
- **stateful(상태 기억)**: 검문소가 “나간 사람”을 기억한다. 그래서 내 요청에 대한 **응답은 자동 허용**된다. 그래서 응답용 인바운드 규칙을 따로 안 만들었고, 아웃바운드 전체 허용도 위험하지 않다.
- **우리 규칙 표**:

  | 방향 | 포트 | 소스 | 뜻 |
  |---|---|---|---|
  | 인바운드 | TCP 80 | `0.0.0.0/0` | 손님 누구나 안내 책자를 보러 올 수 있음 |
  | 인바운드 | TCP 22 | 내 IP `/32` | 관리자문은 내 사원증만 |
  | 아웃바운드 | 전체 | `0.0.0.0/0` | 로봇이 부품(패키지·이미지)을 사러 나감 |

- **3중 안전장치** (실수로도 못 여는 구조):
  1. 템플릿 `Rules.RejectPublicSsh` — SSH가 `0.0.0.0/0`이면 **스택 생성 자체를 거부**
  2. 파라미터 `AllowedPattern` — `/32` 형식만 허용
  3. `scripts/deploy-stack.sh` — 전체 공개·root 배포·다른 스택/키 이름을 스크립트가 차단

**④ 평가에서 이렇게 말한다**

> “인바운드는 두 개가 전부입니다. 80은 인터넷 전체, 22는 제 개인 IP 하나(`/32`)만. SG는 연 것만 통과하는 구조라서 **이 목록이 곧 방침**이고, 전체 포트 허용도 IPv6 인바운드도 없습니다. 아웃바운드는 패키지·이미지를 받아야 해서 열어뒀는데, SG가 상태를 기억하기 때문에 응답은 자동으로 나가고 인바운드 노출과는 다릅니다. 그리고 SSH 전체 공개는 템플릿 규칙과 배포 스크립트가 거부하게 만들어 실수로도 못 엽니다.”

**⑤ 꼬리질문 대비**

| 질문 | 답 |
|---|---|
| “내 IP가 바뀌면?” | “SSH가 막힙니다. 전체로 여는 대신 소스를 갱신하거나, 아예 문을 안 여는 SSM Session Manager로 전환합니다.” |
| “`/32`랑 `/0` 차이?” | “`/32`는 주소 딱 하나, `/0`은 전부. 숫자는 고정하는 비트 수입니다.” |
| “아웃바운드가 열려 있으면 위험하지 않나?” | “데이터가 몰래 나가는 것은 막아야 할 대상이라면 별도 통제가 필요합니다. 다만 이번 과제 위험의 핵심은 **인바운드 노출**이고, 그건 2개 규칙으로 최소화했습니다.” |

## 1-④ 외부 접속 — A(브라우저) 또는 B(`/health` 200) 중 택1

**① 뜻**: 인터넷 건너편에서 **실제로 찾아올 수 있는지**를 확인하는 것. A는 “사람이 보는 화면”, B는 “기계가 읽는 신호”.

**② 비유**: A는 **가게 간판·진열이 보이는지**, B는 **전화 걸면 “영업 중”이라고 답하는지**. 둘 중 하나만 증명해도 된다(문항도 “제출자가 선택한 방식”이라고 명시).

**③ 실제 동작**

- **A(브라우저)**: `http://<퍼블릭 IP>` → Nginx가 `index.html`을 내려주고 브라우저가 렌더링.
- **B(`/health`)**: `curl -i http://<IP>/health` → `HTTP/1.1 200 OK` + 본문 `OK`. Nginx 설정 그대로:
  ```nginx
  location = /health {
      default_type text/plain;
      return 200 "OK\n";     # 파일도, DB도 필요 없음 — 항상 같은 답
  }
  ```
- **`200`이 뜻하는 것**: HTTP 상태 코드 “요청 성공”. 서버가 응답을 정상적으로 만들었다는 신호다. (참고: 404 = 파일 없음, 502 = 뒤의 서버가 죽음)
- **왜 B가 자동화에 좋나**: 응답이 `OK` 한 단어라서 **기계가 판정하기 쉽다**. `aws-verify.sh`, Docker `HEALTHCHECK`, `cfn-signal`이 모두 같은 `/health`를 쓴다 → **한 곳에서 만든 신호를 배포·검증·모니터링에 재사용**.
- 우리 증거: A `11-browser-home.jpg`, `30-current-browser-home.jpg` / B `12-external-health-200.txt`, `27-iam-network-health.txt`.

**④ 평가에서 이렇게 말한다**

> “둘 다 준비했고 대표는 A입니다. 브라우저에서 페이지가 뜨고, 같은 서버의 `/health`는 200 `OK`를 돌려줍니다. B는 `/health` 한 경로로 **Docker 헬스체크, 배포 성공 판정, 외부 자동 검증이 모두 같은 신호를 재사용**하게 하려고 남겼습니다.” (라이브 서버가 없으면 “정리 규정에 따라 삭제했습니다”를 **먼저** 말한다.)

**⑤ 꼬리질문 대비**

| 질문 | 답 |
|---|---|
| “A/B 아무거나 되나?” | “문항이 택1로 되어 있고, 구현이 같아서 둘 다 됩니다. 대표는 사람이 보는 화면인 A로 골랐습니다.” |
| “200이면 뭐가 증명되나?” | “인터넷 → 대문 → 마당 → 검문소 → 집 → 로봇까지 **전 구간이 한 번에 통과**했다는 뜻입니다.” |
| “지금 보여달라” | “미리 재배포해 뒀습니다”가 1순위. 아니면 삭제 사실을 먼저 밝히고 삭제 전 증거를 제시. |

## 1-⑤ 정리 체크리스트 최소 5종(EC2/EBS/EIP/IGW/VPC)

**① 뜻**: 실습이 끝난 뒤 **돈이 나갈 수 있는 것을 전부 없애고**, 그 과정을 목록으로 증명하는 것.

**② 비유**: 이사 후 **반납 목록** — 가구(EC2), 창고(스토리지), 대문 열쇠까지. “안 쓴 물건은 없다”도 **확인해서** 적어야 한다.

**③ 실제 동작**

- **무엇이 돈이 되나**: ① 실행 중인 인스턴스(초 단위) ② **남아 있는** EBS 볼륨 ③ 할당된 Elastic IP ④ 스냅샷 ⑤ 퍼블릭 IPv4 주소 ⑥ NAT/ALB/RDS(시간+사용량).
- **`terminated` vs `stopped`** — 가장 중요한 구분:

  | 상태 | 컴퓨터 | 디스크(EBS) | 요금 |
  |---|---|---|---|
  | `running` | 켜짐 | 있음 | 나감 |
  | `stopped` | 꺼짐 | **남아 있음** | 디스크 요금 나감 |
  | `terminated` | 삭제 | 함께 삭제(우리 설정) | 안 나감 |

  우리 템플릿은 `DeleteOnTermination: true`(인스턴스 삭제 시 볼륨도 삭제) + `Encrypted: true` + gp3 8GiB. 그래서 **terminate만 하면 디스크까지 정리**된다.
- **스택이 지우는 것 vs 내가 지워야 하는 것**:
  - 스택(`b6-1-learning`) 삭제 → VPC·IGW·서브넷·RT·SG·EC2·EBS·ENI·**시작 템플릿(LT)** 까지 전부 삭제
  - **스택 밖** → **키페어 `b6-1-key`** (우리가 별도로 만든 것) → 따로 삭제해야 한다
  - 실제로 LT·키페어 삭제 권한이 없어서 중간에 실패(`37·40`)했고, 권한 보정 후 재시도로 완료(`43·44`)
- **“미생성”과 “미확인”의 차이**: EIP는 **만들지 않았다.** 그래도 “해당 없음”으로 넘기면 안 되고 **조회해서 0개임을 보여줘야** 한다(증거 `44`).
- 한 줄 결론: **“스택 DELETE_COMPLETE + EC2 terminated + 볼륨 0개 + 조회 0개 + Billing 예상 0.00”** 이 5종 정리의 증거 세트다.

**④ 평가에서 이렇게 말한다**

> “체크리스트에 실제 리소스 ID를 적고 대조했습니다. EC2는 terminated, EBS는 삭제되어 서울 볼륨 0개, IGW는 분리 후 삭제, VPC·서브넷·SG·라우트 테이블 조회 0개, 시작 템플릿·키페어도 0개입니다. EIP는 **만든 적이 없어서** 미생성이고, 대신 조회에서 0개임을 확인했습니다. 마지막으로 Billing 예상 USD 0.00까지 확인했습니다.”

**⑤ 꼬리질문 대비**

| 질문 | 답 |
|---|---|
| “stop만 해도 되나?” | “아니요. stop은 디스크가 남아 과금됩니다. terminate까지 해야 합니다.” |
| “EIP는 지웠나?” | **“만들지 않았습니다. 미생성이고 조회 0개로 확인했습니다.”** (여기서 “지웠습니다”는 거짓이 된다) |
| “정말 다 지운 건가?” | “서울 리전에서 확인한 목록 기준입니다. 전 리전·전 서비스 0개라고는 주장하지 않습니다.” |

# 항목 2 — 설명 (쉬운 해설)

## 2-① “외부 → IGW → Subnet → EC2” 흐름

**① 뜻**: 그림을 가리키며 **손님이 우리 집 안내 책자까지 도착하는 길**을 순서대로 말하는 것.

**② 비유**: 도로 → 대문 → 마당 안내판 → 현관 검문소 → 집 → 응대 로봇 → 안내 책자.

**③ 단계별 “막히면 이렇게 보인다” 표** (이 표가 4-①의 뿌리다)

| 단계 | 없는 경우 | 겉으로 보이는 증상 |
|---|---|---|
| 대문(IGW) 미연결 | 인터넷과 단절 | 접속 시간 초과(timeout) |
| 안내판(`0.0.0.0/0`→IGW) 없음 | 나가는 길·응답 경로 없음 | timeout, 요청은 가는데 응답 없음 |
| 검문소(SG) 80 미허용 | 패킷이 버려짐 | timeout (거부 응답도 안 옴) |
| 퍼블릭 IP 없음 | 집 주소가 없음 | 접속 자체가 불가 |
| 로봇(Nginx/컨테이너) 죽음 | 포트에 아무도 없음 | **connection refused** (즉시 실패) |
| 파일 없음 | 안내 책자가 없음 | **404 Not Found** |

→ **“timeout은 바깥(네트워크), refused는 안쪽(프로세스)”** 라고 기억하면 점검 순서가 자연스러워진다.

**④ 평가에서 이렇게 말한다**: (60초 대본 그대로)
> “브라우저 → 인터넷 → IGW(대문) → 퍼블릭 서브넷의 라우트 테이블(안내판) → SG(현관 검문소)의 80 허용 검사 → EC2 퍼블릭 IP → Docker가 게시한 컨테이너 80번 → Nginx → `index.html` 또는 `/health`. 한 단계라도 빠지면 실패하므로, 장애가 나면 이 순서대로 바깥에서 안쪽으로 확인합니다.”

## 2-② 보안 그룹을 어떤 기준으로 최소화했나

**① 뜻**: “왜 이 두 줄만 있고 나머지는 없나”를 **기준(원칙)** 으로 설명하는 것.

**② 비유**: 현관 문 관리를 세 가지 규칙으로 하는 것 — **① 쓰는 문만 연다 ② 열쇠는 필요한 사람에게만 준다 ③ 쓰고 나면 잠근다.**

**③ 최소화의 3축**

| 축 | 우리 선택 | 근거 |
|---|---|---|
| 포트 수 | 80(서비스) + 22(관리)만 | 실제로 쓰지 않는 포트는 열 이유가 없음 |
| 소스 범위 | 80=`/0`(공개 서비스), 22=`/32`(내 IP) | 공개가 목적인 것만 공개, 관리는 최소 |
| 유지 시간 | 임시로 연 규칙은 즉시 제거 | “열어두고 잊기”가 사고의 주원인 |

**④ 평가에서 이렇게 말한다**
> “기준은 셋입니다 — 서비스 포트만 연다, 관리 포트는 소스를 최소화한다, 임시로 연 것은 즉시 닫는다. 그래서 인바운드는 80과 22 두 줄이고, 80만 인터넷 전체, 22는 제 IP 하나입니다. 아웃바운드는 부품 조달(패키지·이미지)용이라 방향이 다릅니다.”

**⑤ 꼬리질문**: “포트와 소스 중 뭐가 더 중요한가?” → “포트 수를 줄이는 게 먼저지만, 관리 포트는 **소스 범위가 실질 방어선**입니다.”

## 2-③ A/B를 골랐고, 그 선택을 위해 뭘 구성했나

**① 뜻**: “선택 → 그 선택을 가능하게 만든 설계”를 연결해서 말하는 것. 선택만 말하고 끝나면 빈 답이 된다.

**② 비유**: “간판 보고 오게 하겠다”고 정했으면, **간판·진열대·조명**을 갖춰야 한다.

**③ 실제 연결(A 선택 시)**

| A를 위해 필요한 것 | 우리 구성 |
|---|---|
| 외부에서 80 통과 | SG 인바운드 80 `0.0.0.0/0` |
| 주소가 있어야 함 | 서브넷 `MapPublicIpOnLaunch: true` + 인스턴스 퍼블릭 IP |
| 컨테이너로 전달 | `docker run -p 80:80` |
| 내용이 있어야 함 | `site/index.html` → `/usr/share/nginx/html` |
| 살아있는지 알려야 함 | `/health` (+ Docker HEALTHCHECK, cfn-signal, 검증 스크립트) |

**④ 평가에서 이렇게 말한다**
> “A를 골랐으니 A가 되도록 구성했습니다 — 80 공개, 퍼블릭 IP 할당, 컨테이너 80 게시, 루트에 index.html. 그리고 어떤 방식으로 골라도 필요할 ‘살아있는지’ 신호를 `/health`로 만들어서 배포 검증과 자동 점검이 같은 신호를 쓰게 했습니다.”

## 2-④ 태그·이름 규칙·체크리스트로 추적한다

**① 뜻**: 리소스가 많아져도 **내 것만 찾아낼 수 있는 체계**를 만들었는지.

**② 비유**: 물건마다 **이름표(태그)**, 창고 칸마다 **접두어(이름 규칙)**, 이사 후 **반납 목록(체크리스트)**.

**③ 실제 동작 — 태그 하나가 3가지 일을 한다**

| 용도 | 어떻게 |
|---|---|
| 찾기 | 콘솔 필터·CLI 필터로 `Project=b6-1`만 조회 |
| 비용 | Cost Explorer에서 태그별 비용 확인 |
| **권한** | IAM 정책 조건으로 `Project=b6-1` 요구 → 태그 없는 리소스는 **변경·삭제 권한 자체가 없음** |

- CloudFormation이 붙이는 `aws:cloudformation:stack-name=b6-1-learning`은 **사용자가 임의로 못 붙이는 예약 태그**라서, 위조 불가능한 잠금장치로 쓸 수 있다.
- 이름 규칙 `b6-1-*`: 스택 `b6-1-learning`, 키 `b6-1-key`, SG `b6-1-web-sg` …
- 체크리스트: 실제 ID를 적어두고 삭제 후 대조.

**④ 평가에서 이렇게 말한다**
> “태그 `Project=b6-1`과 CloudFormation 스택 태그, 이름 규칙 `b6-1-*`, 체크리스트 세 가지를 씁니다. 특히 태그는 표시용이 아니라 **IAM 조건**이라서 태그가 없는 리소스는 손댈 권한이 없습니다. 스택이 지워도 남는 키페어처럼 스택 밖 리소스는 따로 추적했습니다.”

# 항목 3 — 이해 심화 (쉬운 해설)

## 3-① Public Subnet의 기본 경로가 왜 필요한가

**① 뜻**: “안내판에 그 한 줄을 왜 꼭 써야 하나”.

**② 비유**: 집에 손님은 들어왔는데, **나가는 길이 없어서 답장을 부칠 우체통이 없는 상태**가 된다.

**③ 실제 동작**
- EC2는 사설 주소(`10.0.1.x`)를 쓴다. 목적지별 경로가 다 있는 게 아니므로 **`0.0.0.0/0`(표에 없는 모든 목적지) 한 줄**이 필요하다.
- 이 경로가 없으면 **응답이 나갈 수 없어서**, 손님 입장에서는 그냥 “응답 없음(timeout)”으로 보인다.
- “퍼블릭”은 플래그가 아니라 **세 조건의 결과물**: ① 라우트 테이블에 `0.0.0.0/0 → IGW` ② IGW가 VPC에 attach ③ 인스턴스에 퍼블릭 IPv4.
- VPC 내부 통신은 `10.0.0.0/16 → local` 경로가 자동으로 있어서 별개다.

**④ 평가에서 이렇게 말한다**
> “사설 IP로는 인터넷 목적지를 알 수 없으니 기본 경로가 필요합니다. 없으면 나가는 길과 응답 경로가 막혀서 접속이 실패로 보입니다. IGW attach와 퍼블릭 IPv4까지 합쳐져야 퍼블릭 서브넷입니다.”

---

## 3-② Security Group과 IAM의 차이, 최소 권한은 왜 필요한가

**① 뜻**: **문지기(네트워크)** 와 **권한 카드(API)** 는 다른 층이라는 것.

**② 비유**: SG는 **건물 경비원**(누가 들어오고 나가는지 검사), IAM은 **사내 시스템 로그인 권한**(어떤 프로그램·창고를 쓸 수 있는지). 경비원에게 인사 잘해도 사내 시스템은 못 여는 것과 같다.

**③ 실제 동작**

| | Security Group | IAM |
|---|---|---|
| 층 | 네트워크(데이터 플레인) | 관리(컨트롤 플레인) |
| 대상 | **패킷** | **API 호출** |
| 단위 | 인스턴스(ENI)에 붙음 | 사람/프로그램(주체)에 붙음 |
| 결과 | 트래픽 통과/차단 | 호출 허용/거부 |

- 그래서 **SG로 80을 열어도 AWS를 조작할 권한은 생기지 않고**, IAM이 아무리 넓어도 네트워크가 막히면 못 들어온다.
- **최소 권한의 목적 = 사고 반경 축소.** 우리는 두 정책(`B61DeployerPolicyRestricted`, `B61Ec2DeploymentPolicy`)에 조건을 걸어 서울 리전·정확한 스택 이름·태그·`t3.micro`·IMDSv2·암호화 gp3 ≤8GiB·키 `b6-1-key`만 허용했다 → 실수로도 다른 VPC나 큰 인스턴스가 안 생긴다.
- IAM 관리·액세스 키 발급·PassRole 권한은 **주지 않았다**.

**④ 평가에서 이렇게 말한다**
> “SG는 네트워크 계층에서 패킷을, IAM은 컨트롤 플레인에서 API 호출을 통제합니다. 층이 달라서 둘 다 최소화해야 합니다. 최소 권한은 사고 반경을 줄이는 장치이고, 실제로 조건으로 리전·스택·태그·인스턴스 타입·암호화 여부까지 제한했습니다. 권한이 부족할 때도 관리자 권한을 붙이지 않고 거부된 작업만 좁혀서 추가했습니다.”

---

## 3-③ SSH(22)나 DB 포트를 `0.0.0.0/0`으로 열면 왜 안 되나

**① 뜻**: “인터넷 전체에 관리 문을 열어두면 무슨 일이 생기는가”.

**② 비유**: 아파트 전체에 우리 집 열쇠를 뿌리는 것. 문 앞에 **도둑 명단이 아니라 순찰 로봇**이 돌아다니고 있다고 생각하면 된다.

**③ 실제 동작**
- 열린 포트는 **몇 분 안에 스캔**된다(쇼단 같은 검색엔진이 열린 포트를 색인한다). SSH를 열면 **하루에도 수천~수만 건의 로그인 시도**가 들어온다.
- DB 포트를 열면 자격 증명을 훔쳐 데이터 유출로 직결된다.
- **포트 번호를 바꾸는 건 보안이 아니다** — 스캔 도구가 전체 포트를 훑기 때문에 잠깐의 회피일 뿐이다.
- “잠깐만 열어두기”가 사고의 주원인이라 과제 제약에도 SSH 소스 제한이 명시되어 있다.

**대안 비교**

| 방법 | 원리 | 비유 |
|---|---|---|
| 내 IP `/32` | 우리 사원증에만 관리자문 허용 | 가족 열쇠만 |
| **SSM Session Manager** | 에이전트가 **밖으로** 연결 → **인바운드 포트를 아예 안 연다** | 관리실이 먼저 전화를 걸어오게 해 두기 |
| Bastion(경유지) | 경유지만 관리 대역 허용 | 경비실 하나만 관리자문 |
| SG끼리 참조 | 앱 계층 SG만 DB SG에 접근 | 부서 카드끼리만 통과 |
| 프라이빗 서브넷 | 아예 인터넷 경로를 안 준다 | 창고는 단지 안에서만 |

**④ 평가에서 이렇게 말한다**
> “인터넷 전체 공개는 즉시 스캔·브루트포스 대상이 되고, 임시 개방을 잊으면 그대로 침해로 이어집니다. 그래서 SSH는 내 IP `/32`만 허용했고, 더 나은 대안으로는 포트를 아예 안 여는 SSM Session Manager가 있습니다. DB는 프라이빗 서브넷과 SG 참조로 앱만 접근하게 하는 게 정석입니다.”

---

## 3-④ “가설→검증” 순서와 로그 활용

**① 뜻**: 문제를 **한 번에 하나씩** 확인해서 원인을 특정하고, 다음에 재현 가능하게 만드는 방법.

**② 비유**: 의사 진단 — 증상 듣고 → 가설 세우고 → **검사하고** → 처방. 검사 없이 약부터 주면 왜 나았는지도, 왜 안 나았는지도 모른다.

**③ 순서와 도구**

| 단계 | 하는 일 | 우리가 쓴 도구/증거 |
|---|---|---|
| 증상 | 무엇이 안 되는지 한 문장으로 | “CloudFormation 업데이트 실패” |
| 가설 | 왜 그럴지 후보 세우기 | “권한이 없다 / 태그 조건이 안 맞는다” |
| 검증 | **읽을 수 있는 근거**로 확인 | CFN 이벤트, IAM dry-run 오류 메시지, 시뮬레이터 |
| 조치 | 최소 범위만 고치기 | 거부된 API·리소스만 허용 추가 |
| 결과 | 재시도로 확인 | 재시도 성공(`43`) |
| 재발 방지 | 체크/문서화 | 배포 전 검증 절차에 추가 |

**실제 3건**: 시작 템플릿 권한(`04→05`) / 네트워크 태그 갱신(`06→08`) / 정리 중 삭제 거부(`37·40→42→43`).
로그 근거: `docker logs b6-1-web`, `/var/log/cloud-init-output.log`, CloudFormation 이벤트.

**④ 평가에서 이렇게 말한다**
> “여러 개를 동시에 고치면 원인을 특정할 수 없고 재현도 안 됩니다. 그래서 증상→가설→검증→조치→결과→재발 방지 순서를 지켰고, 검증은 dry-run·이벤트·로그 같은 **읽을 수 있는 근거**로만 했습니다. 실제 3건을 이 순서로 해결했고 실패 이력도 지우지 않았습니다.”

# 항목 4 — 응용·장애 대응 (쉬운 해설)

## 4-① 외부 접속이 안 될 때 점검 순서

**① 뜻**: “안 될 때 어디부터 볼 것인가”를 **순서**로 답하는 것.

**② 비유**: 택배가 안 왔을 때 — ① 도로가 뚫렸나 ② 경비실에서 막았나 ③ 주소가 맞나 ④ 집에 사람이 있나 ⑤ 기록을 보자.

**③ 왜 이 순서인가**: **바깥 → 안쪽**. ① 외부에서 확인 가능한 것 ② 흔한 것 ③ 싼 것부터. 서버 접속은 마지막.

| 순서 | 확인 | 방법 | 증상 단서 |
|---|---|---|---|
| 0 | 배포 자체 | CloudFormation 이벤트 | 생성 실패면 여기서 끝 |
| 1 | 라우팅 | RT `0.0.0.0/0`→IGW, attach | 전부 timeout |
| 2 | SG | 80 인바운드·소스, 서브넷 ACL | 전부 timeout |
| 3 | 주소 | 퍼블릭 IPv4, (도메인) DNS | 접속 자체 안 됨 |
| 4 | 프로세스 | `docker ps -a`, `curl localhost/health`, 포트 리슨 | refused면 프로세스 문제 |
| 5 | 로그 | `docker logs`, Nginx access/error, cloud-init | 404·502면 내용/프록시 문제 |

**④ 평가에서 이렇게 말한다**
> “바깥에서 안쪽으로 봅니다. 먼저 배포 이벤트, 그다음 ① 라우팅 ② SG ③ 퍼블릭 IP/DNS ④ 서버 프로세스(`docker ps`, 내부 `/health`, 포트) ⑤ 로그 순서입니다. timeout은 바깥 문제, refused나 404는 안쪽 문제라는 단서로 좁힙니다.”

## 4-② IAM 권한이 부족할 때 “무작정 올리지 않고” 최소 범위 찾기

**① 뜻**: 거부당했을 때 **관리자 권한을 붙이지 않고** 정확히 필요한 만큼만 여는 절차.

**② 비유**: 결재가 반려되면 반려 사유를 읽고 **그 항목만** 고친다. “사장 권한으로 다 열자”는 최악이다.

**③ 5단계**

| 단계 | 내용 | 도구 |
|---|---|---|
| 1 | 거부된 API·리전 확인 | 오류 메시지(“…no identity-based policy allows…”) |
| 2 | 대상 리소스 ARN 특정 | 스택/리소스 ID |
| 3 | ARN을 모르는 **생성** 작업은 **조건**으로 제한 | 태그 조건, 인스턴스 타입, 암호화 여부 |
| 4 | 그 범위만 허용 추가 | Access Analyzer 검증 |
| 5 | 재검증 | dry-run, 시뮬레이터, 실제 재시도 |

- **왜 관리자 권한이 최악인가**: ① 사고 반경이 커진다 ② **무엇이 필요했는지 영영 모르게 된다**(재현·설명 불가).
- 실제 3건 모두 이 방식으로 해결했고, `AdministratorAccess`는 사용하지 않았다.

**④ 평가에서 이렇게 말한다**
> “오류 메시지에서 거부된 API를 확인하고, 대상 ARN을 특정하고, 생성 작업처럼 ARN을 미리 알 수 없으면 태그·타입 같은 **조건**으로 범위를 좁힙니다. 그 문장만 추가한 뒤 Access Analyzer와 dry-run으로 재검증합니다. 권한을 넓히는 방식은 사고 반경이 커지고 재현성도 잃어서 쓰지 않았습니다.”

## 4-③ 인스턴스를 2대로 늘리면? — 병목과 추가 구성

**① 뜻**: “현재 구조에서 무엇이 한계인지”와 “무엇을 추가해야 하는지”.

**② 비유**: 가게 손님이 늘면 — 점원 1명(병목), 가게 1칸(건물 하나), 간판이 점원 목에 걸림(주소가 서버 직결). 대응은 **건물 2칸 + 안내 데스크(ALB) + 채용 관리(오토스케일링)**.

**③ 병목 3개**

1. 인스턴스 **1대 = 단일 장애점** (한 대 죽으면 서비스 종료)
2. 서브넷이 **AZ 1곳** → 다중 AZ 불가
3. 공인 IP가 인스턴스에 **직결** → 교체·확장이 경직

**④ 추가 구성 4개**

| 추가 | 왜 |
|---|---|
| AZ별 서브넷 2개 이상 | 서로 다른 동에 서버를 둬서 한 동 장애에도 서비스 유지 |
| **ALB + 타깃 그룹** | 트래픽 분산 + **헬스체크로 죽은 서버 자동 제외**(우리 `/health` 재사용) |
| Auto Scaling 그룹 | 인스턴스 수·교체를 자동 관리 |
| **EC2는 ALB의 SG에서만 80 허용** | 뒷문 직접 공개를 막아 정문(ALB)을 우회 못 하게 |

```
        인터넷
          │
      [ ALB ]  ← 공인 주소는 여기에만 (80/443)
      ┌───┴───┐
 [EC2 1대] [EC2 2대]   ← 각각 다른 AZ, 80은 ALB SG에서만
   (AZ-a)   (AZ-c)
```

- **정적 사이트라 세션 상태가 없다** → 어느 서버로 보내도 같은 응답, 수평 확장이 단순하다. 대가는 ALB 비용(+LCU)과 구성 복잡도.

**⑤ 평가에서 이렇게 말한다**
> “병목은 ① 인스턴스 1대(단일 장애점) ② 서브넷이 한 AZ ③ 퍼블릭 IP 직결입니다. 2대로 늘리려면 AZ별 서브넷 2개, ALB와 타깃 그룹(헬스체크는 기존 `/health` 재사용), Auto Scaling 그룹이 필요하고, 공인 트래픽은 ALB만 받고 EC2는 ALB SG에서만 80을 허용하도록 바꿉니다. 정적 사이트라 세션이 없어서 확장은 단순하고, 대가는 비용과 복잡도입니다.”

## 4-④ Billing에 예상치 못한 비용이 찍혔다면

**① 뜻**: “돈이 샜을 때 어디를 의심하고 어떻게 찾아 없애는가”.

**② 비유**: 관리비 명세서에 이상한 항목 → ① 어느 **서비스**인지 ② 어느 **기간**인지 ③ 어느 **이름표(태그)** 인지 좁혀서 범인 찾기.

**③ 무엇이 돈이 되나 (의심 순서)**

| 순위 | 대상 | 왜 새는가 |
|---|---|---|
| 1 | **미연결 Elastic IP** | 쓰지 않아도 할당만 되어 있으면 과금 |
| 2 | **NAT Gateway** | 시간당 + 처리 데이터당 (실수로 만들기 쉬움) |
| 3 | **RDS** | 시간당 + 스토리지 |
| 4 | **스냅샷·미사용 EBS** | 존재하는 동안 GB-월 |
| 5 | 퍼블릭 IPv4 주소 | 주소당 시간 요금 |
| 6 | 데이터 전송 | 리전 밖/인터넷으로 나가는 트래픽 |

- **찾는 법**: Cost Explorer/Bills에서 기간·서비스·리전으로 좁히고, 태그 `Project=b6-1`으로 소유 확인 → Release/삭제.
- **반영 지연**: 청구는 즉시가 아니라 **하루~며칠 늦게** 반영된다 → 삭제 후 **다음 날 재확인**이 필수.
- 우리 상태: EIP/NAT/ALB/RDS **미생성**, 삭제 후 조회 0개, 10월 **예상** USD 0.00, 잔여 크레딧 119.97(누적 사용 0.03). `46`·`47`.

**④ 평가에서 이렇게 말한다**
> “서비스·기간·리전별로 좁히고 태그로 소유를 확인합니다. 의심 순서는 미연결 EIP, NAT, RDS, 스냅샷·미사용 볼륨, 퍼블릭 IPv4, 데이터 전송입니다. 삭제·Release 후에는 청구 반영이 늦기 때문에 다음 날 다시 확인합니다. 이번 실습은 EIP·NAT·ALB·RDS를 만들지 않았고, 정리 후 IAM으로 0.00(예상)을 확인했습니다.”

# 부록 — 한 줄 용어 사전

| 용어 | 한 줄 뜻 |
|---|---|
| CIDR `/0`, `/24`, `/32` | `/뒤 숫자` = 고정하는 비트 수. 작을수록 넓은 범위(`/0`=전부, `/32`=한 개) |
| 인바운드/아웃바운드 | 들어오는 트래픽 / 나가는 트래픽 |
| stateful | 앞서 나간 연결을 기억해 응답을 자동 허용하는 성질(SG) |
| `running`/`stopped`/`terminated` | 켜짐 / 꺼졌지만 디스크 남음 / 삭제(디스크도 삭제) |
| `200` / `404` / `502` | 성공 / 파일 없음 / 뒤의 서버 문제 |
| `healthy` | Docker가 HEALTHCHECK로 검사해 통과한 상태 |
| dry-run | 실제로 하지 않고 “했다면 허용될까”만 확인하는 API 옵션 |
| Launch Template | 인스턴스 생성 조건(태그·네트워크·IMDSv2 등)을 미리 정해둔 틀 |
| IMDSv2 | 인스턴스 메타데이터 접근에 토큰을 요구하는 보안 방식 |
| `cfn-signal` | 인스턴스가 CloudFormation에 “완료”를 알리는 신호 |
| 태그 조건 | IAM에서 태그 유무·값으로 권한을 제한하는 장치 |
| 조회 0개 | 삭제·미생성을 “확인”하는 방법(안 하는 것과 다름) |
